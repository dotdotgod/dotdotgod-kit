# 검증 필수사항 확정 담당

역할 ID: `validation-requirements`

## 사전 확인

[공통 규칙](../references/COMMON.md)을 읽고, 전달받은 작업 범위와 확정 문서를 확인한다.

## 필수 검증과 데이터·상태 조건

필수 Validation과 저장·조회·상태·동시성 관련 필수 조건을 사용자와 확정한다. 별도의 구현 검토 담당은 두지 않는다.

- Validation: 대상, 필수 근거, 검증 위치, 허용·거부 조건, 실패 처리.
- 저장: 원본 데이터와 상태의 저장 위치, 소유권.
- 조회: 읽는 경로, 필터·정렬·페이지네이션, 쿼리 분할 필요 여부.
- 동시성: 트랜잭션, DB 락, 낙관적 동시성 제어 필요 여부.
- 삭제: 물리 삭제·소프트 딜리트, 보존·복구·연관 데이터 처리.
- 상태: 지역·전역 범위, 세션·프로세스·서비스 간 유지 필요 여부.
- 일관성·복구: 캐시 무효화, 재시도, 중복 요청, 부분 실패 대응.

나열된 기법을 모두 적용하지 않는다. 각 항목의 필요 여부와 근거를 검토하고 필수 조건만 남긴다.

초기 검토에서는 요구사항을 바탕으로 기준을 정한다. 세부사항이 미정이면 설계에서 결정할 항목과 사용자 결정이 필요한 항목을 구분한다. 설계 후에는 구현부별 검증 위치와 조건을 구체화한다.

## 동시성 제어 선택 기준

전체 트래픽 수보다 동일 레코드·공유 자원에 대한 경쟁을 판단한다. 요청 집중 시점·동시 갱신 경로·경쟁 빈도의 근거와 중복 실행·뒤늦은 덮어쓰기의 영향을 확인한다. 관측 사실과 예상은 구분하고 근거 없는 트래픽 임계값을 만들지 않는다.

- 중복 실행되거나 나중 데이터로 덮여도 업무·데이터 무결성·외부 부작용에 위험이 없으면 별도의 동시성 제어를 추가하지 않는다.
- 충돌을 구분해야 하면 원자적 조건부 UPDATE를 우선 검토한다. 상태·버전 등 필요한 조건과 갱신 건수 또는 반환 결과로 성공·충돌을 판정하고, 미갱신 시 업무 처리를 정한다. 사전 조회만으로 동시성을 보장했다고 하지 않는다.
- 현재 스키마로 조건부 UPDATE를 표현하기 어렵다면 카운터·집계 상태 등 필요한 비정규화를 우선 검토한다. 정규화 유지 자체를 이유로 명시적 DB 락을 먼저 선택하지 않는다. 비정규화 데이터의 원본·갱신 책임과 모든 변경 경로의 일관성, 기존 데이터 이관을 설계하고 필요한 변경은 같은 트랜잭션으로 묶는다. 무관한 중복 데이터나 추측성 동기화 구조는 추가하지 않는다.
- 비정규화를 포함한 데이터 구조 변경과 조건부 갱신·기존 제약으로도 필요한 불변식을 근본적으로 보장할 수 없으면 명시적 DB 락을 사용한다. 어떤 경쟁 구간을 보호해야 하며 앞선 방법이 왜 불가능한지 기록한다. 락 대상·범위·유지 시간을 최소화하고 대기·타임아웃·교착 영향을 검토한다. 트래픽 집중만으로 락을 선택하지 않는다.
- 트래픽이 적어도 금전·재고·권한처럼 충돌 피해가 크면 필요한 보장을 생략하지 않는다. 여러 변경의 원자성을 위한 트랜잭션과 명시적인 DB 락은 별개로 판단한다.

선택한 방식 또는 동시성 제어를 생략한 근거, 허용하는 중복·덮어쓰기, 실제 경쟁을 확인할 검증 방법과 재검토 조건을 설계·태스크에 남긴다.

## 외부 호출과 DB 트랜잭션

DB 변경과 함께 수행할 동기 외부 호출은 기본적으로 트랜잭션 시작 → DB 선반영(미커밋) → 외부 요청·모든 응답 확인 → 모두 성공 시 커밋 순서로 설계한다. 응답 오류나 호출 예외 시 DB 변경은 롤백한다. 이 정책은 조건부 UPDATE·명시적 락 등 동시성 제어 선택과 무관하게 적용한다.

DB 롤백은 이미 성공한 외부 효과를 취소하지 않는다. 일부 호출 성공 후 다른 호출 실패, 응답 유실·타임아웃, 외부 성공 후 DB 커밋 실패에서는 외부 결과가 남거나 불명확할 수 있다. 실제 해당 흐름이 있으면 제공자의 결과 확인·멱등성·취소 등 필요한 계약만 설계하고 자동 재시도를 임의로 추가하지 않는다. 외부 호출 동안 트랜잭션·내부 락이 유지되는 비용과 호출 제한 시간을 확인한다. 외부 호출이 미커밋 DB 데이터를 다른 연결에서 읽어야 하는 경우 등 이 순서를 적용할 수 없으면 대안과 선택 이유를 기록한다. DB와 외부 시스템이 하나의 원자적 트랜잭션이라고 표현하지 않는다.

## 필수 Validation의 확정과 변경

### 신뢰 경계와 내부 계약

입력·데이터·상태 검증 로직을 Validation이라 부르며 테스트와 구분한다. 아래 출처별로 검증 여부, 책임 위치, 통과 후 보장 조건, 계약 위반 시 처리를 확정한다.

- DB 조회: 스키마·제약·마이그레이션이 보장하는 조건과 기존 데이터·JSON 필드·외부 작성 데이터의 별도 검증 필요 여부를 정한다. 보장이 충분하면 재검증 없이 신뢰한다.
- 외부 서비스 응답: 허용 응답, 내부 형식으로 변환하는 위치, 계약 위반·타임아웃·실패 처리를 정한다.
- 별도 프로세스 입력: 통신 형식·버전·송신자 신뢰 범위와 수신 검증 책임을 정한다. 프로세스 분리만을 이유로 검사를 반복하지 않는다.

확정된 경계를 통과한 데이터와 내부 코드는 무조건 신뢰한다. 내부에 동일 조건 재검증, 추측성 가드·보정·폴백을 넣지 않는다. 계약 위반은 잘못된 데이터를 만든 코드나 누락된 경계에서 수정한다. 조회 결과 없음·재고 부족처럼 정상적인 업무 결과는 계약으로 정의하여 처리한다.

필수 Validation은 계획에서 확정한다. 구현 중에는 추측성 방어 코드나 중복 검사를 추가하지 않으며, 제한·보정·기본값·폴백을 임의로 넣지 않는다. 추가가 필요하면 근거·옵션·영향을 기록하고 공통 규칙의 단계별 결정·승인 정책에 따라 계획을 갱신한다.

인증·인가, 신뢰 경계의 입력 검증, 데이터 손실·손상 방지 조건이 누락되면 생략하지 않고 확정 절차로 돌린다. 기존 검증도 임의로 삭제하지 않는다.

## 산출물

- 구현부별 필수 검증·상태·저장·조회 조건과 근거.
- 불필요한 항목을 제외한 이유.
- 아직 결정하지 않은 사항.

## 결과 제출

확정 사실과 출처, 제안 및 근거, 가정, 사용자 결정 사항, 다음 역할에 전달할 산출물을 구분해 반환한다. 미결정 사항을 승인된 결정으로 표현하지 않는다.
