# 역할 기반 플래닝

한국어 초안. 계획이 산출물이다. 구현하지 않는다. 사용자와 요구사항·설계를 확정하고, 새 세션에서도 수행할 수 있는 태스크와 플래닝 작업 최종 완료 보고서를 작성한다. 기존 계획 모드, 프로젝트 지침, 권한을 준수하며 이를 대체하지 않는다.

## 역할 배정 전 필수 확인

[역할 목록](roles/README.md)과 [역할 공통 규칙](references/COMMON.md)을 먼저 읽는다. 상대 링크는 링크가 적힌 문서의 디렉터리를 기준으로 해석한다. 배정할 역할의 개별 정의를 읽고, 위임할 에이전트에 해당 정의와 필요한 프로젝트 근거를 전달한다. 역할은 책임 단위이며 인원 수를 뜻하지 않는다.

## 실행 환경 확인

1. 현재 환경에 실제로 노출된 에이전트 생성·위임 도구를 확인한다.
2. 병렬 실행, 결과 수집, 독립 컨텍스트, 도구·권한 제약을 확인한다.
3. 에이전트별 모델 지정 지원 여부와 사용 가능한 모델을 확인한다.
4. 사용자가 전달한 설정과 이번 호출의 모델 지정 요청을 확인한다.
5. 역할별 요청 모델과 실제 실행 모델, 제약을 사용자에게 알린다.

도구가 있다고 추측하거나 임의로 설치하지 않는다. 요청 모델을 사용할 수 없으면 추가 확인 없이 설정된 기본 모델로 전환하고, 기본 모델이 없거나 사용할 수 없으면 실행 환경의 기본 모델을 사용한다. 요청 모델·실제 모델과 전환 이유를 기록하고 알린다. 실행 환경의 기본 모델도 사용할 수 없으면 해당 위임을 차단하고 독립 작업은 계속한다. 멀티 에이전트를 사용할 수 없으면 제약을 알리고 하나의 에이전트가 역할별로 분리하여 순차 검토한다. 이를 실제 병렬 실행이나 독립 리뷰로 표현하지 않는다.

역할별 모델 요청이 있으면 [모델 설정 지침](references/MODELS.md)을 읽는다. 설정 형식은 제안 단계이며, 설정 파일 이름과 탐색 위치는 미정이다. 자동 설정 로더는 제공하지 않는다.

## 자율 진행과 결정 경계

확정 범위 안에서 되돌릴 수 있는 조사·문서 작성·태스크 분해는 자율적으로 진행하고 결과와 근거를 기록한다. 요구사항 조사와 설계에서는 사용자 결정이 남아 있으면 계속 질문한다. 사실은 직접 조사하고, 선행 결정이 끝난 질문을 선택지·영향·권고안과 함께 묶어 묻는다. 침묵이나 미응답을 승인으로 취급하지 않는다.

태스크 단계의 변경·비가역 실행은 [공통 규칙](references/COMMON.md)의 자율 결정·승인 경계를 따른다. 요구사항·가정 옵션과 설계 옵션, 선택 이유·근거·다른 방법과 제외 이유를 기록하고 진행한다. 필수 범위를 넘는 작업은 필요성과 범위 내 대안도 최종 보고서에 남긴다. 실행 세션은 비가역 단계만 승인 충족 전까지 대기하고 허용된 승인 준비와 독립 작업은 지시를 기다리지 않고 진행하도록 태스크에 명시한다. 계획 스킬 자체는 구현하지 않는다.

## 진행 절차와 사용자 확정 게이트

### 페이즈 A: 환경 확인

위 실행 환경 확인 결과를 바탕으로 사용할 도구, 역할별 모델, 병렬 또는 순차 실행 방식을 정한다.

### 페이즈 B: 초기 기준 병렬 검토

사용자 요구사항 담당, 데이터 요구사항 담당, 검증 필수사항 확정 담당이 같은 요청과 프로젝트 근거를 병렬로 검토하며, 병렬 실행이 불가능하면 순차 수행한다. 각 역할의 제안을 합의된 결정으로 취급하지 않는다.

세 역할의 실제 산출물과 검토 완료 / 결정 필요 / 차단됨 / 미수집 상태를 확인한다. 필수 결과가 누락되면 완료로 처리하지 않는다. 중복 질문과 충돌을 정리하고, 사실은 조사로 확인하며 선행 결정이 끝난 질문만 한 라운드로 묻는다. 사용자 확정이 필요한 사항이 남으면 설계로 넘어가지 않는다. 선택지와 각각의 영향, 권고안을 제시하고 사용자와 확정한다. 요구사항이 바뀌면 관련 역할이 재검토한다. 설계에서 구체화하기로 합의한 사항은 언제 결정할지 기록한다.

종료 조건: 요구사항, 우선순위, 범위, 완료 기준, 초기 필수 검증 기준을 정리하고 사용자 결정이 필요한 사항을 해소한다.

### 페이즈 C: UX 설계와 리뷰

전체 설계 지휘자가 UX 설계 담당에게 설계를 배정한다. UX 설계 리뷰어와 보안 설계 리뷰어의 검토를 거쳐 수정한다. 사용자 결정이 필요한 경우에만 멈춰 질문하고 설계를 확정한다.

### 페이즈 D: Presentation Layer/Data Network Layer 설계와 리뷰

확정된 UX와 공유 계약을 바탕으로 Presentation Layer와 Data Network Layer 설계 중 병렬로 진행할 수 있는 작업을 배정한다. 각 영역의 설계 리뷰어와 보안 설계 리뷰어가 설계를 평가한다. 전체 설계 지휘자는 평가 결과를 해당 설계 담당에게 전달하고, Presentation Layer와 Data Network Layer 사이의 계약을 조율한다. 사용자 결정이 필요한 경우에만 멈춰 질문하고 관련 설계를 확정한다.

Presentation Layer 화면 설계에는 반드시 ASCII 아트를 포함한다. 화면이 없는 작업은 적용 제외 근거를 남긴다.

검증 필수사항 확정 담당이 설계에 맞춰 검증 위치·조건 및 저장·조회·상태 정책을 구체화한다. 기준 변경이 필요하면 사용자 확인 후 관련 설계에 반영한다.

### 페이즈 E: 테스트 설계와 전체 리뷰

테스트 설계 담당이 필요한 유닛 테스트와 실제 환경의 사용자 시나리오 검증을 설계한다. TDD는 유닛 테스트에만 적용하고 자동화 E2E 스위트는 기본 제외한다. 테스트 설계 리뷰어와 보안 설계 리뷰어가 검증 범위와 보안 조건 누락을 평가한다. 전체 리뷰 지휘자는 영역별·보안 리뷰를 모아 계약이 일치하는지, 누락이나 중복이 있는지 검토한다. 전체 설계 지휘자는 관련 설계 담당에게 수정을 배정하고, 해당 리뷰어는 영향받는 부분을 다시 검토한다. 남은 미결정 사항은 사용자와 확정한다.

종료 조건: 역할별 설계·테스트·필수 검증의 일관성을 확인하고 사용자 결정이 필요한 사항을 해소하여 설계를 확정한다. 이후 확정 범위 안의 되돌릴 수 있는 계획 작업에는 별도 사용자 승인 게이트를 두지 않는다.

### 페이즈 F: 태스크 계획

작업 계획자가 확정된 요구사항과 설계 안에서 영역별 태스크와 페이즈, 병렬 그룹, 의존관계와 순서를 자율적으로 확정한다. 사용자에게 추가 질문이나 실행 계획 승인을 요청하지 않고 결과를 보고한다.

종료 조건: 조사 / 구현 / 검증을 구분하고 유형별 확인 방법·기대 결과·통과 기준을 포함한다. 구현 태스크는 변경 대상·계약·검증 방법·관련 리뷰 결과를 갖추고, 미조사 범위는 조사 태스크로 남긴다. 새 세션에 전달할 수 있는 태스크 명세와 실행 순서를 완성한다. 구현을 자동으로 시작하지 않는다.

### 페이즈 G: 최종 완료 보고

[최종 완료 보고서 작성 담당](roles/completion-reporter.md)이 확정 계획·태스크와 역할별 실제 결과를 확인하고 [보고서 양식](references/TEMPLATES.md#최종-완료-보고서-양식)으로 플래닝 작업 최종 완료 보고서를 작성한다. 비가역 실행의 선택 이유·근거·대안과 승인 조건을 빠짐없이 연결한다. 차단·미수집 결과가 있으면 부분 완료 또는 차단으로 보고한다. 보고서는 `docs/archive/report/YYYY-MM-DD/<task-slug>/PLANNING.md`에 작성하고 같은 디렉터리의 `README.md` 목차 및 현재 계획과 연결한다. 이후 구현 배치·전체 보고와 구분하여 보존한다. 페이즈 G에서는 계획을 archive로 이동하지 않는다. 관련 README 인덱스를 갱신한다. 구현·검증·main 머지가 남아 있으면 계획 작성 완료와 전체 작업 완료를 구분하고 해당 종료 작업을 실행 세션에 인계한다. main 머지 시 머지 또는 squash 커밋 본문에 보고서·계획 경로, 선택 근거·대안·범위 변경, 승인·검증 결과와 남은 위험을 포함하도록 계획한다. archive가 Git에서 무시되면 강제 추가하지 않고 커밋 본문에 핵심 내용을 자족적으로 남긴다. 계획 경로와 보고서 경로를 전달하고 종료한다. 구현이나 머지를 이 스킬이 직접 시작하지 않는다.

## 작성 및 종료 규칙

- [리뷰 기준](references/REVIEW.md)을 설계자와 리뷰어에게 전달한다.
- DB 조회·외부 서비스 응답·프로세스 입력의 신뢰 정책을 계획에서 확정하고, 경계 이후 내부 코드는 무조건 신뢰한다. 중복 검증 대신 계약 위반의 원인이나 누락된 경계를 수정하도록 계획한다.
- [계획서·태스크 양식](references/TEMPLATES.md)으로 결과를 작성한다. 계획 작성 전에 사용 가능한 `dotdotgod config <root> --json`으로 해석된 설정을 확인하고 해석된 출력의 `config.areas`(원본 설정 파일에서는 `memory.areas`) 중 활성 계획 영역(`role: active-task-intent`) 경로를 우선 사용한다. CLI가 없으면 현재 AI 에이전트의 도구·프로젝트 지침·접근 가능한 설정에서 관련 계획 경로를 찾는다. 설정 해석 오류는 설정 부재로 간주하지 않고 원인을 보고한다. 확인된 설정에 계획 경로가 없으면 기존 `docs/plan`을 사용한다. `docs/plan`도 없으면 실행 에이전트가 제공하는 계획 경로를 사용한다. 에이전트 계획 경로를 추측하지 않고 실제 제공된 경로를 확인하여 기록한다. 선택한 계획 루트의 `<task-slug>/README.md`에서 활성 계획을 관리하고 설계·태스크 문서는 같은 디렉터리에 둔다. 계획 루트의 `README.md`에 계획을 등록하고 작업 디렉터리의 `README.md`를 목차로 유지한다. 완료된 계획은 `docs/archive/plan/<task-slug>/`로 옮긴다.
- 요구사항 조사·설계에서는 사용자 결정이 모두 해소될 때까지 질문한다. 설계 이후 태스크 분해·순서·병렬 구성은 확정 범위 안에서 자율 진행한다. 설계 이후 변경은 옵션·선택 근거·영향을 기록하여 진행하며, 비가역 실행의 승인 조건과 준비 작업은 구분하여 계획한다. 프로젝트 권한·안전 승인 규칙은 그대로 따른다.
- 모든 단계에 역할·영역·목표·산출물·의존관계·완료 기준을 명시한다.
- 계획에서 확정한 필수 Validation만 태스크에 포함한다. 새 필수 검증이 발견되면 근거·옵션·영향을 기록하고 관련 기준·설계·테스트를 갱신한다. 설계 확정 후에는 기존 계획·설계를 근거로 대안을 비교·선택하여 진행하고 변경된 리뷰와 선택 이유를 최종 보고서에 기록한다. 도구·프로젝트의 필수 권한·안전 승인은 그대로 준수한다. 인증·인가, 신뢰 경계의 입력 검증, 데이터 무결성·손실 방지 조건은 누락되어도 생략하지 않고 확정 절차로 돌린다. 기존 검증도 임의로 삭제하지 않는다.
- 요구 변경 시 사용자 요구사항 담당이 기존 요구와의 모순 및 선후 관계를 재검토하고, 관련 설계·리뷰·태스크를 갱신한다.
- 구현 단계에서는 확정된 태스크와 [구현 담당 역할](roles/implementer.md)을 새 실행 세션에 전달하고 해당 역할을 사용하도록 명시한다. 이 스킬은 구현 세션을 자동으로 실행하지 않는다. 계획을 위한 역할 위임은 위 절차에 따른다.
