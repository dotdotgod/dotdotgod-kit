# 리뷰 공통 기준

리뷰에서는 요구 근거 없이 추가된 구성(AI slop)과 불필요한 방어적 설계를 우선 검토한다.

추상화는 현재 어떤 계약을 지키거나 복잡성을 숨기는지, 제거했을 때 무엇이 사라지는지 확인한다. 구현 개수만으로 인터페이스를 금지하지 않으며 현재 근거가 없는 추상화는 추가하지 않는다. 전달만 하는 계층, 여러 곳의 동일 상태 소유, 수동 동기화 목록을 점검하되 계층이나 래퍼를 일괄 삭제하지 않는다. 설계 대안이 실제로 갈리는 경우에만 후보와 선택 이유·수용한 비용을 기록한다. 모든 작업에 여러 후보나 프로토타입을 강제하지 않는다.

각 발견은 설계 위치, 관련 요구·규칙, 근거, 영향, 권고를 포함한다. 계약 위반 / 개선 제안 / 미확인 위험을 구분하고, 증거는 직접 관측 / 소스 확인 / 추론 / 미확인으로 표시한다. 실행하지 않은 설계를 검증 완료로 표현하지 않는다. 보안 리뷰와 영역별 원보고를 보존하며 지휘자는 상충 의견의 조정 이유를 남긴다.

## AI slop: 근거 없이 덧붙인 구성

- 요구사항과 연결되지 않는 기능·구성.
- 근거 없는 계층·추상화·확장 지점.
- 기존 패턴으로 해결할 수 있는데 새로 만든 구조.
- 중복 문서·작업·테스트.
- 구체적 결정 없이 일반론으로 채운 설계.
- 목적 없는 UI와 불필요한 사용자 단계.

## 근본 원인과 완결성

버그 수정 계획은 관련 사용처를 조사하고 증상별 우회 처리 대신 공통 원인을 해결하는지 확인한다. 호출부·설정·테스트·마이그레이션을 포함한 변경 범위가 완결되어야 하며, 짧은 diff나 적은 파일 수만으로 좋은 설계라고 판단하지 않는다. 단순화를 이유로 명시적 요구사항, 보안·권한, 신뢰 경계 검증, 데이터 무결성·손실 방지, 접근성, 필요한 검증을 누락하지 않았는지 확인한다.

## 불필요한 방어적 설계

경계 정책은 검증 필수사항 확정 담당의 [신뢰 경계와 내부 계약](../roles/validation-requirements.md#신뢰-경계와-내부-계약)을 따른다. 내부 코드는 무조건 신뢰한다. 기존 검증의 필요 근거를 찾지 못한 것과 불필요함이 입증된 것을 구분한다.

- 확정된 필수 Validation에 포함되지 않은 검사.
- 내부 계약에서 이미 보장하는 조건을 중복 확인하는 검사.
- 오류를 숨기는 기본값·보정·폴백.
- 근거 없는 재시도·예외 처리·상태 분기·복구 경로.

확정된 필수 Validation과 보안·데이터 무결성·손실 방지 조건은 유지한다. 새 필수 조건을 발견하면 검증 필수사항 확정 담당에게 전달하여 기준 변경을 검토하고, 공통 규칙의 단계별 결정·승인 정책에 따라 반영한다.

리뷰 결과는 유지·수정·삭제·사용자 결정 필요로 분류하고 판단 근거를 남긴다. 설계를 확정하려면 간결성뿐 아니라 요구사항 충족, 계약 일치, 접근성, 실행 가능성도 확인해야 한다.
