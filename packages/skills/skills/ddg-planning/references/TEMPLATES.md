# 계획서와 태스크 양식

## 계획서 양식

계획 작성 전에 사용 가능한 `dotdotgod config <root> --json`으로 해석된 설정을 확인한다. CLI가 없으면 현재 AI 에이전트의 도구·프로젝트 지침·접근 가능한 설정에서 관련 계획 경로를 찾는다. 설정 해석 오류는 설정 부재로 간주하지 않고 보고한다. 해석된 출력의 `config.areas`(원본 설정 파일에서는 `memory.areas`) 중 활성 계획 영역(`role: active-task-intent`) 경로를 우선 사용하고, 설정에 계획 경로가 없으면 기존 `docs/plan`을 사용한다. `docs/plan`도 없으면 실행 에이전트가 제공하는 계획 경로를 사용한다. 에이전트 계획 경로를 추측하지 않고 실제 제공된 경로를 확인하여 기록한다. 선택한 계획 루트의 `<task-slug>/README.md`에 계획을 작성한다. 관련 설계·태스크는 같은 디렉터리에 두고 계획 루트와 작업 디렉터리의 `README.md` 목차를 갱신한다. 계획 범위 완료 후 `docs/archive/plan/<task-slug>/`로 이동하고 최종 보고서와 상호 연결한다.

```markdown
# 작업 계획

## 상태와 확정 기록
## 배경과 목적
## 6하원칙으로 정리한 요구사항
## 우선순위와 포함·제외 범위
## 요구사항 충돌과 결정 기록
## 역할·책임·작업 영역
## 필수 Validation과 저장·조회·상태 정책
- 경계별 출처·검증 책임·통과 후 보장·실패 처리:
- DB 조회·외부 응답·프로세스 입력의 신뢰 정책:
- 내부 코드 신뢰와 중복 검증 제외:
## UX 설계
## Presentation Layer 설계와 ASCII 아트
## Data Network Layer 설계
## 선택한 해법의 적용 범위·알려진 한계·재검토 조건 (실제 한계가 있을 때만)
## 유닛 테스트와 사용자 시나리오 검증 설계
- 필요한 테스트와 제외 근거:
- 관측 지점·보장 범위·독립 기대값 근거:
- 실제 환경에서만 확인할 조건:
## 영역별·보안 리뷰와 전체 리뷰 결과
- 계약 위반·개선 제안·미확인 위험:
- 요구 출처·설계 위치·증거 수준·영향·권고:
## 페이즈별 실행 계획
### 페이즈 이름
- 목표와 우선순위:
- 담당 역할과 작업 영역:
- 태스크와 산출물:
- 선행 조건과 차단 이유·실행 순서:
- 병렬 그룹과 충돌 방지 조건:
- 독립 완료 조건과 통합 방법·완료 기준:
## 일정과 수행자 (미정인 항목은 미정으로 표시)
## 위험·가정·미결정 사항
- 미결정 질문과 선행 결정·다음 확인 시점:
- 아직 구체화되지 않은 사항:
- 보류와 제외 범위:
## 태스크 명세 목록
## 최종 완료 보고서 경로
```

## 최종 완료 보고서 양식

```markdown
# 작업 결과 보고서

## 보고 대상: 계획 작성 / 구현 배치 / 전체 작업
## 대상 태스크·배치 ID와 포함 범위
## 해당 범위 상태: 완료 / 부분 완료 / 차단
## 전체 계획 상태와 남은 범위
## 산출물: 계획·설계·태스크 경로
## 확정 요구사항·설계와 결정 출처
## 요구사항·가정 옵션과 설계 옵션
- 선택한 옵션·이유·근거·영향:
- 다른 방법과 제외 이유:
- 필수 범위 밖 작업의 필요성과 범위 내 대안:
## 태스크 순서·의존관계·병렬 그룹
## 비가역 실행의 결정 기록 (해당 없으면 없음)
- 관련 태스크·대상·영향과 비가역인 이유:
- 선택 이유·근거와 결정 출처:
- 다른 옵션과 제외 이유:
- 복구 가능 범위:
- 실행 전 승인·권한 조건과 실제 실행 여부:
## 역할별 결과·리뷰와 검증 증거
- 설계 확정 후 변경 내용·영향받는 기존 리뷰·갱신 결과:
## 차단·미결정·미검증 사항과 남은 위험
## 다음 실행 세션의 착수 조건
## 아카이브·main 머지 기록
- 실제 보고서: docs/archive/report/YYYY-MM-DD/<task-slug>/<PLANNING.md | BATCH_<ID>.md | FINAL.md> (보고 대상에 맞는 파일 하나)
- 보고 목차: docs/archive/report/YYYY-MM-DD/<task-slug>/README.md
- 완료 계획: docs/archive/plan/<task-slug>/ (완료 전에는 현재 경로)
- 상호 링크·관련 README 인덱스 갱신:
- main 머지 상태·커밋 (미수행이면 미수행):
- 머지/squash 커밋 본문에 남길 결정·대안·범위 변경·승인·검증·위험 요약:
## 수행·미수행 작업과 다음 착수점 (계획 보고는 구현 수행으로 간주하지 않음)
```

보고서 작성은 비가역 실행의 승인을 대신하지 않는다. 계획·배치·전체 보고는 날짜별 작업 디렉터리의 README 목차에서 연결하되 `PLANNING.md`, `BATCH_<ID>.md`, `FINAL.md`로 구분하여 서로 덮어쓰지 않는다. 동일 날짜·태스크·보고 대상의 반복 보고는 같은 파일을 갱신하되, 중요한 상태 변경과 검증 증거는 시각이 있는 이력으로 추가하여 이전 근거를 보존한다. README에는 최신 상태와 각 보고서 경로를 유지한다. 부분 완료도 보고서를 남기며, 완료 표시·태그는 실제 완료한 범위에만 적용한다.

## 사용자 시나리오 검증 양식

```markdown
# 사용자 시나리오: <제목>

## 확인할 요구사항과 보안 조건
## 수행 방식: 사람 / 에이전트
## 실제 지원 도구·환경과 필요한 권한
## 초기 데이터·계정·세션 및 병렬 격리
## 수행할 행동
## 기대 화면·상태·저장 결과
## 관측 지점과 성공·실패 기준
## 수집할 증거
## 종료 후 정리
## 미검증 항목과 남은 위험
```

## 실행 세션에 전달할 태스크 양식

```markdown
# 태스크: <제목>

## 목표
## 태스크 유형: 조사 / 구현 / 검증
## 수행 역할과 역할 정의의 정확한 경로 (구현 태스크는 implementer 필수)
## 실행 상태: 조사 필요 / 착수 가능 / 진행 중 / 완료 / 차단
## 선행 태스크와 착수 조건
## 단계별 승인 조건과 승인 충족 준비 작업
- 비가역 단계·대기 조건:
- 허용된 승인 준비·조건 확인 작업:
- 대기 중 계속할 독립 작업:
## 요구·설계 변경의 옵션·선택 근거·대안·영향
## 필수 범위 밖 작업의 필요성과 범위 내 다른 방법
## 참조할 확정 요구사항·설계·프로젝트 지침
## 작업 영역·쓰기 허용/금지 범위
## 수행 내용 (조사: 근거·결론·미확인 사항 / 구현: 변경 내용 / 검증: 관측·판정)
## 구현 착수 근거 (구현 태스크만): 변경 대상·계약·검증 방법·관련 리뷰 결과
## 선택한 해법의 한계·재검토 조건 (해당할 때만, 확정 설계 참조)
## 필수 Validation과 실패 처리
## 테스트 (필수)
- 확인할 요구사항·완료 기준:
- 같은 태스크에서 작성·수정할 유닛 테스트 (없으면 확정된 제외 근거):
- 실행할 테스트와 명령 또는 수행 절차:
- 테스트 데이터·환경과 독립적인 기대값 근거:
- 통과 기준과 남는 검증 범위:
- 사용자 시나리오·실제 환경 검증의 수행 내용 또는 의존 태스크:
## 비가역 실행 (해당 없으면 없음)
- 대상·영향과 비가역인 이유:
- 선택 이유와 근거·결정 출처:
- 다른 옵션과 제외 이유:
- 복구 가능 범위:
- 실행 전 승인·권한 조건 (보고는 승인 아님):
## 제외 범위와 변경 금지 계약
## 산출물과 독립·통합 완료 기준
## 병렬 작업 주의사항과 공유 파일
## 차단 조건과 처리 방법 (필수 승인 준수·선택 근거와 영향 기록·독립 작업 계속)
## 결과 보고
- 변경 내용:
- 검증 결과:
- 미검증 항목:
- 남은 위험:
```

새 실행 세션이 이전 대화 없이도 작업할 수 있도록 필요한 결정을 태스크에 적거나 접근 가능한 확정 문서의 정확한 위치를 참조한다.

구현 태스크에는 [구현 담당 역할](../roles/implementer.md)의 접근 가능한 정확한 경로를 기입하고 실행 세션이 읽고 사용하도록 한다. 조사·검증 태스크에는 적합한 역할과 증거·판정 절차를 지정하고 코드 변경을 완료 조건으로 요구하지 않는다. 미조사 범위는 조사 태스크로 남기고 구현 준비 완료로 표시하지 않는다. 각 태스크는 유형에 맞는 테스트·확인 항목을 포함한다. 기능과 필요한 유닛 테스트는 같은 태스크·실행 세션에서 구현하고 실행한다. 코드 작성만 끝났다고 태스크를 완료로 표시하지 않으며, 확정된 테스트 결과와 미검증 항목을 보고한다. 테스트를 통과시키기 위해 기대 결과나 완료 기준을 임의로 약화하지 않는다.
