# 역할 공통 규칙

이 문서의 상대 링크는 이 파일이 있는 디렉터리를 기준으로 해석한다.

역할은 책임, 영역은 변경 대상을 뜻한다. Presentation Layer는 화면·상호작용, Data Network Layer는 저장·조회·데이터 통신 계약을 담당한다. 이 명칭으로 코드 디렉터리나 불필요한 계층을 강제하지 않는다.

## 최소하지만 완결된 계획·설계

- 기능·설정·계층을 현재 요구사항과 연결한다. 근거 없는 미래 확장 기능은 제외한다.
- 기존 프로젝트 패턴 → 표준 라이브러리·플랫폼 기능 → 설치된 의존성 → 새 구현 순으로 검토한다. 각 해법이 요구·보안·유지보수 조건에 적합한지 확인하고, 부적합하면 이유를 기록한 뒤 다음 대안을 검토한다. 코드량뿐 아니라 이해·운영·검증·복구 비용을 포함해 요구를 충족하는 가장 단순한 해법을 선택한다.
- 관련 코드·계약·사용처·데이터 흐름을 조사한 뒤 최소화한다. 수정량이 작다는 이유로 영향 범위도 작다고 가정하지 않는다.
- 호출부·설정·테스트·마이그레이션 등 함께 변경할 대상을 계획에 포함한다. 불필요한 작업은 줄이되 문제 해결에 필요한 범위를 누락하지 않는다.
- 단순 해법에 실제 한계가 있으면 적용 범위·알려진 한계·재검토 조건을 기록한다. 재검토 조건은 합의된 목표나 관측 가능한 상황으로 작성하고, 근거 없는 임계값을 만들지 않는다. 전체 비용이 비슷한 대안이라면 경계 조건에 더 정확한 쪽을 선택한다.

명시적 요구사항, 보안·권한, 신뢰 경계 검증, 데이터 무결성·손실 방지, 접근성, 필요한 검증은 단순화를 이유로 생략하지 않는다. 계획 단계에서는 이 기준으로 해법을 선택하며 구현을 시작하지 않는다.

## 위임과 결과 수집

위임에는 목표, 범위, 확정 문서와 버전, 산출물, 완료 기준, 쓰기 가능한 파일, 재위임 허용 여부를 전달한다. 위임된 역할은 질문 후보·선택지·권고안을 반환하고, 주 에이전트가 중복과 의존관계를 정리한다. 요구사항·설계 단계에서는 사용자 결정이 필요한 질문을 묻고 확정 답변을 관련 역할에 전달한다. 설계 확정 후에는 아래 단계별 자율 결정 규칙에 따라 판단·근거를 전달하며, 도구·프로젝트의 필수 권한·안전 승인은 별도로 준수한다. 병렬 실행이 불가능하면 역할별 산출물을 구분하여 순차 수행한다. 긴 결과는 요약과 접근 가능한 문서 포인터로 반환한다.

결과 상태는 검토 완료 / 결정 필요 / 차단됨 / 미수집으로 구분한다. 지휘자는 실제 산출물을 확인한다. 필수 역할의 결과가 차단되거나 미수집이면 완료로 처리하지 않는다. 새 세션에 전달하는 문서에는 비밀값을 넣지 않고 필요한 권한과 비밀정보를 받을 위치만 적는다.

## 구현 세션 인계

구현을 맡기는 태스크에는 [구현 담당 역할](../roles/implementer.md)의 접근 가능한 정확한 참조를 포함하고, 실행 세션은 이를 읽고 사용한다. 계획을 위한 설계·리뷰 역할은 구현을 시작하지 않는다. 구현 결과와 검증·추가 제약의 근거는 주 에이전트와 최종 완료 보고서 작성 담당에게 전달한다.

조사와 구현은 별도 태스크로 배정한다. 구현 착수 전 변경 대상·계약·검증 방법·관련 리뷰 결과를 확인하고, 준비된 태스크는 승인된 범위 안에서 진행한다. 전체 조사가 끝나기를 기다리거나 배치마다 재승인을 요구하지 않는다. 읽기 전용 조사 지시와 구현 배정이 충돌하면 제한을 우회하거나 반복 설득하지 않고 확정 태스크를 새 구현 세션에 전달한다.

## 결정 기록

결정은 한 곳에 기록하고 관련 설계·태스크는 그 결정을 참조한다. 미결정 질문, 선행 결정 때문에 아직 구체화하지 못한 사항, 보류, 제외 범위를 구분하고 다음 확인 시점을 남긴다.

- 역할 목록을 확인한 다음 관련 역할 정의를 읽고 책임을 배정한다.
- 작업에 필요한 역할과 영역만 사용하며, 제외할 경우 이유를 기록한다.
- 결과를 작성할 때는 확정 사실, 근거, 제안, 가정, 미결정 사항을 구분한다.
- 요구사항 조사·설계에서는 사용자 결정이 남아 있으면 계속 질문하여 해소한다. 사실은 직접 조사하고, 선행 결정이 끝난 질문을 선택지·영향·권고안과 함께 묻는다. 침묵을 승인으로 간주하지 않는다. 설계·리뷰 완료 이후 확정 범위 안의 되돌릴 수 있는 계획 작업은 추가 승인 없이 자율 진행하고 근거를 기록한다.
- 변경된 결정은 영향받는 요구사항·설계·테스트·태스크에 반영한다.
- 담당자, 일정, 사용할 수 있는 도구를 임의로 지어내지 않는다.
- 적합한 역할이 없으면 요구사항·설계 단계에서 추가 역할을 제안한다. 사용자 결정이 필요한 경우 확인하고, 이후에는 확정된 책임 범위 안에서 작업을 배정한다.
- 참조 문서와 확정 결정의 출처를 남긴다. 이전 대화만으로 작업이 가능하다고 가정하지 않는다.

리뷰 역할은 [리뷰 기준](REVIEW.md)을 추가로 읽는다. 요구사항·설계 단계의 누락이나 충돌에 사용자 결정이 필요하면 질문한다. 설계 확정 후 요구·설계 변경이 필요하면 요구사항·가정 옵션과 설계 옵션을 나열하고 선택 이유·근거·대안의 제외 이유·영향을 결정 기록과 최종 보고서에 반영하여 진행한다. 필수 범위를 넘어가는 작업은 필요한 이유와 범위 안에서 해결할 다른 방법의 검토 결과를 추가한다. 변경된 결정은 관련 설계·검증·태스크에 반영한다. 설계 확정 후 결정은 사용자에게 유보하지 않고 기존 확정 계획·설계를 근거로 여러 안을 비교하여 선택하고 구현 세션은 그 결정으로 진행한다. 실질적인 변경은 영향받는 기존 리뷰를 갱신하고 변경 전후·리뷰 결과를 최종 보고서에 남긴다. 영향 없는 리뷰는 유지한다. 이 자율 결정은 도구·프로젝트의 필수 권한·안전 승인을 대신하지 않는다.

실행 세션은 태스크의 선행 조건과 단계별 승인 조건을 구분한다. 비가역 단계는 승인 조건 충족 전까지 대기하고, 허용된 승인 준비·조건 확인 작업과 독립 작업을 지시 대기 없이 진행한다. 필요한 사람의 승인·권한 부여를 스스로 만들어내지 않는다. 계획 스킬은 구현하지 않고 이 실행 규칙을 태스크에 전달한다. 보고서 작성은 실행 승인이 아니며 보안·권한·데이터 손실 방지 규칙을 우회하지 않는다.
