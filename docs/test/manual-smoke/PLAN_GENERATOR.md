# Plan Generator Smoke Tests

1. Run `/plan-goal --help` and confirm usage is shown without creating `docs/plan/` files or sending a Stage 01 authoring prompt.
2. Run `/plan-goal` with no args and confirm the first-request editor opens when custom UI is available; without a request, confirm no follow-up is sent.
3. Run `/plan-goal add staged authoring smoke` and confirm the UI first shows startup progress such as `generating plan slug`, then creates an LLM-proposed kebab-case path, or a deterministic request-derived fallback such as `docs/plan/add-staged-authoring-smoke/README.md` when no model proposal is available; confirm it creates `.dotdotgod-plan/01_INTAKE.md` through `dotdotgod plan stage create`, stores `currentStage: 01-intake`, marks status `active`, and immediately sends the Stage 01 authoring prompt with a bounded `Current stage checkpoint context` block for `.dotdotgod-plan/01_INTAKE.md`.
4. On the next `agent_end`, confirm Stage 01 authoring is not sent a second time and Plan Mode does not open its execute/stay/refine/cancel review while `/plan-goal` is active.
5. Run `/plan-goal --stop` and confirm the generator stops, clears the shared workflow flag, and Plan Mode can resume normal execution review behavior. During an active generator run, press Esc/app interrupt or run no-arg `/plan-goal` and confirm the generator records `status: input-waiting`, preserves `currentPlan/currentStage`, keeps workflow suppression active, and resumes the same stage from the next user message.
6. Run `/plan-goal docs/plan/<task>` and confirm non-README path-like input is treated as a new request. Then run `/plan-goal docs/plan/<task>/README.md`: missing README paths should warn without creating a slug, existing README paths with no checkpoint should create `01_INTAKE.md` and queue Stage 01 in place, existing paths with a checkpoint should resume that stage with bounded checkpoint context, and completed final checkpoints should not queue another stage.
7. Complete Stage 01 intake with request summary, goal, likely targets, unknowns/risks, and next-stage context; confirm `agent_end` creates `.dotdotgod-plan/02_CONTEXT_LOAD.md` through `dotdotgod plan stage create`, advances to `02-context-load`, and sends one handoff with bounded `Next stage checkpoint context` content that treats `.dotdotgod-plan/**` as internal stage state context.
8. Complete Stage 02 context-load by updating the durable plan artifact for readers and `.dotdotgod-plan/02_CONTEXT_LOAD.md` for validation; confirm the checkpoint has `Stage: 02-context-load`, `Status: completed`, `Updated:`, `## Memory Reads`, `## Impact Candidates`, `## Related Files`, and `## Stage 02 Construction Checklist` with completed evidence rows. The preferred checkpoint checklist row format is `- [x] Category: evidence`, including exact Stage 02 categories `Memory reads`, `Impact candidates`, `Related files`, and `Boundary risk`; compatibility forms such as completed table/status rows may validate, but generator prompts should emit the canonical bullet form. Confirm noncanonical durable README formatting does not by itself block advancement when checkpoint evidence is complete.
9. Continue Stage 03 through Stage 05 and confirm each pass completes the current `.dotdotgod-plan/NN_STAGE_NAME.md` checkpoint before advancing and creates the next checkpoint before handoff. Stage 04 should produce handoff-ready durable implementation design plus completed checkpoint evidence with code touchpoints, data/state flow, edge cases, tests, and atomic completion criteria. When the design spans multiple implementation parts, confirm Stage 04 splits the durable plan into task-local support markdown files and `README.md` links them. Stage 05 should read prior stage context and write durable Workstream Handoff Contract content outside `.dotdotgod-plan`, while `.dotdotgod-plan/05_WORKSTREAM_HANDOFF.md` carries the machine-readable required sections and checklist evidence. For split plans, confirm the durable/checkpoint content includes a Workstream Map with at least two `Workstream ID:` fields, Shared Context, Workstreams with structured fields such as `Purpose:`, `Required context:`, `Allowed edits:`, `Forbidden edits:`, `Tasks:`, `Validation:`, `Handoff output:`, and `Dependencies:`, an Integration Sequence with `Step:`, `Validation:`, and `Handoff:`, Todo Contract, and Stage 05 Construction Checklist. Workstream handoffs should identify one primary handoff file per subagent where appropriate and give phase-based implementation expectations that avoid requiring each subagent to inspect the whole plan. For no-split plans, confirm Stage 05 records `Split decision: no`, `No-split rationale:`, and a concrete Todo Contract. Stage 05 completion should remain terminal: it clears or completes the current stage and does not send another handoff.
10. Add a structured unresolved user decision such as `DecisionOwner: user` plus `DecisionState: unresolved`, or `BlockerType: user-decision` plus `Status: blocked`, and confirm `/plan-goal` does not advance. Harmless prose words such as `TBD`, `undecided`, `decision needed`, `미정`, or `결정 필요` should not be treated as machine-readable blockers unless the structured marker is present. It should record `status: input-waiting`, preserve `currentPlan/currentStage`, ask the user a concrete question with options, and resume the same stage after the answer.
11. Force retry and malformed evaluation results after bootstrap and confirm `sendUserMessage` is emitted from `agent_end` with bounded current checkpoint context, store status remains `active`, the breaker increments, `currentStage` is preserved, and the breaker cap stops as blocked after 5 loops.
12. Force a user-input blocked result and confirm the store records `status: input-waiting`, preserves `currentPlan/currentStage`, keeps `/plan-goal` workflow suppression active, and does not queue a follow-up until the user provides more input. Then send relevant follow-up input and confirm the same stage resumes with bounded current checkpoint context. Confirm `/plan-goal --stop`, completed workflows, and retry-exhausted blocked states do not auto-resume.
13. Confirm `/plan-generator --help` is no longer registered as a Pi command; use `/plan-goal` for new and resumed staged generator work.
14. Re-run the Plan Mode boundary checks: `/plan <request>` must not auto-run `/plan-goal`, and Plan Mode must not write `.dotdotgod-plan` stage state context files.
