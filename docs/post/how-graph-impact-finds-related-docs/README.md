# graph impact는 변경 파일에서 함께 검토할 항목을 어떻게 찾는가

**Language:** [English edition](ENGLISH.md)

**Published:** [Velog](https://velog.io/@vgb3766/graph-impact%EB%8A%94-%EB%B3%80%EA%B2%BD-%ED%8C%8C%EC%9D%BC%EC%97%90%EC%84%9C-%ED%95%A8%EA%BB%98-%EA%B2%80%ED%86%A0%ED%95%A0-%ED%95%AD%EB%AA%A9%EC%9D%84-%EC%96%B4%EB%96%BB%EA%B2%8C-%EC%B0%BE%EB%8A%94%EA%B0%80)

자연어 질문이 있을 때는 의미 검색으로 관련 문서를 찾을 수 있다. 구현을 변경한 뒤에는 이 파일과 함께 어떤 스펙, 아키텍처, 테스트와 검증 명령을 확인해야 하는지가 핵심 질문이 된다. **`dotdotgod graph impact`는 변경 파일을 출발점으로 이유가 있는 제한된 검토 목록을 만들며, 문서 목차를 변경에서 원문으로 이동하는 역방향 지도처럼 사용한다.**

파일명 검색만으로는 이 질문에 답하기 어렵다. 코드와 문서가 같은 이름을 사용하지 않을 수 있고, 하나의 변경이 여러 패키지와 검증 경로에 연결될 수 있기 때문이다.

여기서 중요한 기반은 사람이 직접 리뷰하고 관리할 수 있는 프로젝트 메모리다. 스펙, 아키텍처, 테스트 문서, README 목차와 추적 관계가 저장소에 남기 때문에 사람과 에이전트가 같은 근거를 읽고 수정할 수 있다. graph impact는 이 관리 가능한 원문에서 다음 검토 경로를 계산한다.

## 변경 파일을 그래프의 시작점으로 사용한다

하나의 파일을 변경했다면 다음 명령으로 관련 항목을 찾을 수 있다.

```bash
dotdotgod graph impact . \
  --changed packages/cli/src/commands/query.mjs \
  --yml
```

여러 파일을 함께 변경했다면 `--changed`를 반복한다.

```bash
dotdotgod graph impact . \
  --changed packages/cli/src/commands/query.mjs \
  --changed packages/cli/src/query/chunks.mjs \
  --yml
```

명령은 중복 경로를 처음 등장한 순서대로 정리하고 최대 20개의 고유한 변경 파일을 받는다. 각 변경 파일은 같은 가중치의 시작점이 된다. 결과에는 변경 파일이 먼저 나타나고, 여러 시작점에 공통으로 연결된 항목은 전체 순위에서 하나로 합쳐진다.

이 방식은 하나의 변경 작업을 구성하는 여러 파일을 함께 계산해 공통으로 중요한 스펙과 테스트를 찾는다.

## 그래프의 관계는 관리되는 프로젝트 흔적에서 나온다

프로젝트 그래프는 사람이 관리하거나 파일 구조에서 결정론적으로 추출할 수 있는 관계로 구성된다. 저장소 전체의 의미 유사도 검색은 `query`가 담당하고, graph impact는 검토 이유를 추적할 수 있는 연결을 사용한다. 그래프는 이 흔적을 읽어 만든 파생 지도이며, 팀은 Markdown 원문과 추적 정보를 리뷰해 관계의 정확성을 직접 관리한다.

| 신호 | 의미 |
|---|---|
| 구조화된 추적 관계 | `implemented_by`, `verified_by`, `related_doc`, 검증 명령 |
| 문서 관계 | Markdown 링크, 제목, README 탐색 경로 |
| 프로젝트 구조 | 패키지, 소스, 테스트, 설정과 리소스 관계 |
| 메모리 정책 | 현재 스펙, 아키텍처, 테스트와 아카이브의 역할 및 우선순위 |
| 결정론적 routing | 경로, 파일명, 제목, README, 메모리 영역과 패키지 이름의 일치 |

사람이 명시한 추적 관계는 경로나 이름에서 추론한 routing hint보다 신뢰도가 높다. 명시적인 연결이 부족할 때 README와 안정적인 프로젝트 용어가 보조 탐색 경로를 제공한다.

따라서 graph impact의 품질은 그래프 알고리즘과 프로젝트 흔적의 관리 상태가 함께 결정한다. 스펙과 테스트가 실제 구현을 가리키고, README가 현재 문서를 안내하며, 파일이 좁은 책임을 가질수록 더 구체적인 결과를 만들 수 있다.

## 검토 가치를 중심으로 순위를 정한다

관련 노드를 전부 출력하면 영향 분석도 또 다른 전체 검색이 된다. 기본 `balanced` 정책은 변경 파일을 seed로 하는 Personalized PageRank와 프로젝트 검토 정책을 결합한다.

```text
변경 파일들
  → 후보 범위 제한
  → multi-seed Personalized PageRank
  → 추적 관계와 검증 정책 반영
  → 검토 가치에 따라 제한된 결과 구성
```

기본 점수의 출발점은 변경 파일에서 계산한 PPR이다. 여기에 명시적인 추적 관계, 테스트와 검증 신호, Markdown 링크와 README에서 확인되는 직접 근접성을 더한다. 경로·제목·메모리 영역·패키지 이름이 일치할 때는 결정론적 routing hint가 보조 신호로 작동한다.

메모리 정책도 순위에 관여한다. 현재 영역의 우선순위와 `fresh`·`stale` 분류를 반영하고, 아카이브 본문에는 감점을 적용한다. 후보 점수를 계산한 뒤 첫 화면에서는 추적 관계, 테스트와 직접 근접성이 있는 항목을 낮은 신뢰도의 routing-only 항목보다 우선한다. 실행 가능한 문서와 파일이 충분하면 의존성 같은 낮은 행동 가능성의 메타데이터 노드가 결과를 차지하지 않도록 제한한다.

기본 정책은 현재 스펙과 검증 경로를 우선하고 아카이브 본문이 첫 결과를 차지하는 것을 줄인다. 여기서 `fresh`와 `stale`은 메모리 영역에 설정한 분류이며 파일 수정 시각과는 무관하다. 프로젝트별 랭킹 설정은 게시 전에 현재 CLI와 설정 스펙이 일치하는지 확인한 뒤 별도의 설정 문서에서 다룬다.

## 결과는 이유가 있는 검토 목록이다

`--yml`은 에이전트가 바로 읽을 수 있는 제한된 구조를 반환한다. 다음은 출력 형태를 설명하기 위한 예시이며 실제 경로, 점수와 이유는 저장소 상태와 설정에 따라 달라진다.

```yaml
impact:
  ok: true
  changed_files:
    - packages/cli/src/commands/query.mjs
  groups:
    docs:
      items:
        - path: docs/spec/cli/QUERY.md
          score: 65.4
          reasons: [implemented_by, routes_to]
    tests:
      items:
        - path: packages/cli/test/e2e.test.mjs
          score: 58.1
          reasons: [verified_by]
  recommended_actions:
    - review_related_docs
    - run_related_tests
    - run_dotdotgod_validate
```

결과는 문서, 세부 동작 계약, 테스트, 파일, 명령과 패키지 리소스처럼 검토 목적에 맞는 그룹으로 나뉜다. `score`와 `reasons`는 각 항목이 포함된 이유를 보여주고, 생략 항목 수는 제한된 출력 밖에도 후보가 있음을 알려준다.

사람이 빠르게 읽을 때는 기본 출력이나 `--compact`가 적합하다. 에이전트 작업 흐름에는 `--yml`, 상세 점수와 자동화 진단에는 `--json`을 사용할 수 있다.

## graph impact와 벡터 검색은 역할이 다르다

`dotdotgod query`는 자연어 질문과 의미가 가까운 문서를 찾는다. graph impact는 변경 파일과 관리되는 관계로 연결된 검토 항목을 찾는다.

| 기능 | seed | 주요 신호 | 결과의 의미 |
|---|---|---|---|
| `query` | 자연어 질문 | 다국어 임베딩 | 질문과 의미가 가까운 문서 |
| `graph impact` | 변경 파일 | 추적 관계, 링크, PPR과 정책 | 변경 후 먼저 검토할 항목 |

기본 graph impact ranking에는 임베딩 유사도를 사용하지 않는다. 경로, 제목, README, 메모리 영역과 패키지 메타데이터를 사용하는 lexical routing은 결정론적으로 계산된다. 임베딩 검색과 그래프 인덱스는 서로 다른 캐시와 실패 경계를 가진다.

이 분리는 검색 결과를 설명 가능하게 한다. 각 결과가 의미 유사도에서 왔는지, 구현·테스트 관계나 README 경로에서 왔는지 구분할 수 있다.

## 높은 점수는 우선 검토 신호다

impact score가 높을수록 먼저 검토할 가치가 크다. 점수는 파일의 파손 여부를 확정하지 않으며, 제한된 결과 밖에도 영향을 받는 항목이 남을 수 있다.

그래프에 등록된 링크와 추적 관계가 부족하거나 하나의 큰 파일이 여러 동작을 동시에 담당하면 결과도 넓고 덜 구체적이 된다. graph impact로 경로를 찾은 뒤에는 관련 스펙의 실제 내용을 읽고 구현과 테스트를 수정한다. 이어서 회귀 테스트를 실행하고 문서 링크와 추적 정보가 현재 상태를 가리키는지 확인한다.

```text
파일 변경
  → graph impact
  → 관련 스펙과 테스트 검토
  → 필요한 코드와 문서 갱신
  → 테스트와 dotdotgod validate 실행
```

그래프 캐시도 파생 데이터다. 그래프 명령은 캐시가 없거나 오래되었을 때 저장소 파일에서 갱신하며, 원본 스펙과 코드는 계속 판단의 기준으로 남는다.

## 영향 분석의 품질도 실제 기대 결과로 측정한다

점수의 산출 이유를 설명하는 것과 실제로 유용한 파일을 상위에 배치하는 것은 각각 검증이 필요하다. 닷닷갓은 체크인된 사례별 기대 결과를 기준으로 graph impact 순위를 평가한다.

| 지표 | 확인하는 내용 |
|---|---|
| `Precision@5/10` | 상위 결과 중 반드시 또는 가급적 검토할 항목의 비율 |
| `Recall@10` | 반드시 검토할 항목을 상위 10개에서 찾은 비율 |
| MRR | 첫 번째 필수 검토 항목이 얼마나 앞에 있는지 |
| `nDCG@10` | 필수·권장 등급과 전체 순서를 함께 반영한 품질 |

평가 스크립트는 현재 결과와 기준선을 비교해 verdict를 제공한다. 측정 결과는 실제 사례가 충분히 쌓인 뒤 프로젝트에 맞는 CI 임계값을 정할 근거가 된다.

## 변경 검토는 역방향 목차에서 시작한다

문서 목차는 제품 질문에서 관련 스펙과 테스트로 이동하는 정방향 지도다. graph impact는 코드와 문서 변경에서 함께 확인할 장으로 돌아가는 역방향 지도다.

두 방향이 연결되어야 스펙, 구현과 테스트가 변경 이후에도 같은 프로젝트 상태를 설명할 수 있다. 이 구조의 핵심은 탐색 지도가 자동으로 계산되더라도 그 근거는 사람이 읽고 고칠 수 있는 문서와 관계로 남는다는 점이다. 팀이 원문을 관리하면 에이전트의 검토 경로도 함께 갱신된다.

> graph impact는 사람이 관리하는 프로젝트 메모리에서 놓치기 쉬운 다음 검토 경로를 찾는다. 최종 영향 판단은 연결된 원문과 테스트를 함께 확인한 결과로 내린다.
