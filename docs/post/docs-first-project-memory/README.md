# Docs-first 프로젝트 메모리에서 벡터 검색의 역할

AI 에이전트를 위한 프로젝트 메모리를 설계할 때 검색 기술부터 선택하기 쉽다. 문서를 임베딩하고 대화를 저장하며 그래프를 만드는 일보다 먼저, 프로젝트 지식이 지속될 원본을 정해야 한다. **닷닷갓은 사람이 검토하고 버전 관리할 수 있는 문서를 원본으로 두고, 검색과 그래프를 필요한 문서로 이동하는 파생 계층으로 사용한다.** 이것이 Docs-first 프로젝트 메모리의 기본 구조다.

**Language:** [English edition](ENGLISH.md)

**Published:** [Velog](https://velog.io/@vgb3766/Docs-first-%ED%94%84%EB%A1%9C%EC%A0%9D%ED%8A%B8-%EB%A9%94%EB%AA%A8%EB%A6%AC%EC%97%90%EC%84%9C-%EB%B2%A1%ED%84%B0-%EA%B2%80%EC%83%89%EC%9D%98-%EC%97%AD%ED%95%A0)

앞선 글에서는 디렉터리, 파일명과 README가 AI 에이전트를 위한 문서 목차를 만드는 방법과 닷닷갓이 그 목차를 현재 상태로 유지하는 방법을 살펴봤다. 이번 글에서는 한 단계 더 나아가 무엇을 프로젝트 메모리의 원본으로 삼고, 무엇을 다시 만들 수 있는 탐색 데이터로 둘지 구분한다.

## 원본과 파생 데이터를 분리한다

프로젝트 메모리에는 수명이 다른 여러 계층이 존재한다.

| 계층 | 예시 | 역할 |
|---|---|---|
| 공유 원본 | `AGENTS.md`, `docs/spec/`, `docs/arch/`, `docs/test/` | 규칙, 제품 동작, 설계 이유와 검증 지식 |
| 로컬 작업 메모리 | `docs/plan/`, `docs/archive/` | 현재 의도와 필요한 역사적 기록 |
| 파생 탐색 데이터 | 그래프 인덱스, 벡터 캐시, manifest | 관련 원문을 찾기 위한 가속 계층 |
| 세션 컨텍스트 | Load 결과와 선택한 본문 | 현재 요청을 위한 일시적인 읽기 범위 |

관리되는 문서는 사람이 읽고 수정하며 리뷰할 수 있다. Git에 포함된 문서는 어떤 변경에서 내용이 달라졌는지 추적할 수 있고, 스펙과 테스트 사이의 관계도 함께 검토할 수 있다.

`.dotdotgod/` 아래의 벡터 캐시는 선택된 Markdown 문단에서 계산되고, 그래프 캐시는 문서 관계뿐 아니라 패키지, 소스, 테스트와 설정 메타데이터도 인덱싱한다. 두 캐시는 검색 속도와 탐색 품질을 높이는 역할을 맡고, 제품 동작과 설계 결정의 권위는 관리 문서와 코드에 남는다.

```text
관리되는 문서
  ├── 관계 추출 → 그래프 인덱스
  ├── 문단 임베딩 → 벡터 캐시
  └── 선택적 읽기 → 세션 컨텍스트
```

화살표의 방향이 중요하다. 관리 문서가 의미를 보존하고, 그래프와 벡터 캐시, 세션 컨텍스트는 그 의미를 현재 작업에 맞게 탐색하고 전달한다.

## 파생 데이터는 다시 만들 수 있어야 한다

원본과 파생 계층을 나누면 실패의 경계도 분명해진다. 벡터 캐시를 삭제해도 Markdown 원문은 남고, 그래프 인덱스가 오래되거나 손상되면 파일에서 다시 만들 수 있다. 의미 검색을 사용할 수 없는 환경에서도 디렉터리 문서 지도와 README 목차를 따라 탐색할 수 있으며, 한 에이전트의 세션이 종료되어도 공유 규칙과 스펙은 저장소에 남는다.

이 복구 가능성은 모델, 임베딩 형식과 에이전트 도구가 바뀌어도 프로젝트의 핵심 지식을 그대로 유지한다. 닷닷갓은 로컬 벡터 캐시와 그래프 캐시를 원문과 분리하고, 소스와 관리 문서, 프로젝트 설정에서 언제든 다시 계산할 수 있게 한다.

## 검색 결과는 답이 아니라 주소다

자연어 검색은 파일명과 질문의 표현이 다를 때 유용하다. 예를 들어 사용자는 “과거 계획을 기본 컨텍스트에서 빼는 이유”라고 질문하지만 관련 문서는 `LOAD_PROJECT.md`와 `MEMORY_AREA_CONFIG.md`라는 이름을 사용할 수 있다. 다국어 임베딩 검색은 표현이 달라도 의미가 가까운 문단을 찾아준다.

그러나 의미가 가깝다는 사실만으로 그 문단이 현재 스펙인지, 과거 계획인지, 검증되지 않은 아이디어인지 판단할 수는 없다. 디렉터리 경로는 문서의 역할을 드러내고, 각 README는 그 영역의 로컬 목차를 제공한다. 메모리 영역은 공유 범위와 `fresh`·`stale` 분류를 나타내며, 명시적인 추적 관계는 스펙과 구현, 테스트를 연결한다.

따라서 검색 결과는 답이 아니라 **읽어야 할 원문의 후보 주소**다. 에이전트는 결과의 경로와 역할을 확인하고 필요한 원문을 읽은 뒤에 판단해야 한다.

## 그래프는 원문을 향한 검토 경로를 만든다

관계 그래프는 변경한 파일과 함께 검토할 스펙, 테스트와 명령을 찾는다. Markdown 링크, README 경로, 패키지 관계와 구조화된 추적 정보가 연결을 만든다.

그래프 점수는 검토 순서를 정하는 우선순위다. 연결 정보의 범위와 품질에 따라 결과도 달라지므로, 최종 판단은 높은 순위의 원본 스펙과 코드, 테스트를 직접 읽고 검증하는 과정에서 이루어진다.

벡터 검색과 관계 그래프는 출발점이 다르다.

| 탐색 방식 | 출발점 | 반환하는 경로 |
|---|---|---|
| 디렉터리 문서 지도와 README 목차 | 알려진 문서 영역 | 하위 디렉터리와 문서, 다음 로컬 목차 |
| 벡터 검색 | 자연어 질문 | 의미가 가까운 문서 |
| graph impact | 변경 파일 | 함께 검토할 문서, 코드와 테스트 |

세 방식은 서로 다른 출발점에서 관리되는 원문으로 이어지는 탐색 경로를 제공한다.

## Load는 원본을 복사하지 않고 읽을 범위를 만든다

Docs-first 구조는 필요한 문서를 선택해서 읽을 때 효과가 커진다. 닷닷갓의 Load는 다음 순서로 현재 작업의 읽기 범위를 줄인다.

1. `AGENTS.md`, 저장소 README와 `docs/README.md` 같은 진입점을 확인한다.
2. 문서 본문보다 먼저 제한된 깊이의 문서 지도를 만든다.
3. 질문이 있으면 의미 검색으로 관련 문서 경로를 좁힌다.
4. 현재 작업에 필요한 계획이나 역사만 선택한다.
5. 에이전트가 필요한 원문의 관련 절을 읽게 한다.

Load 결과는 현재 세션과 질문에 맞춘 일시적인 탐색 결과다. 다음 작업에서는 같은 원본 문서에서 새로운 읽기 경로를 구성한다.

## 프로젝트 메모리의 신뢰도는 원본의 위치에서 시작된다

AI 프로젝트 메모리의 품질을 검색 정확도만으로 평가하면 중요한 질문을 놓친다. 검색 결과가 가리키는 원문을 사람이 직접 검토할 수 있어야 하고, 현재 스펙과 과거 기록은 경로만으로도 역할이 구분되어야 한다. 검색 인덱스를 지운 뒤에도 프로젝트 지식이 남아야 하며, 에이전트가 바뀌어도 같은 원본과 규칙에 접근할 수 있어야 한다.

Docs-first 프로젝트 메모리는 신뢰할 수 있는 원본 위에서 벡터 검색, 그래프와 Load를 탐색 도구로 활용한다.

> 관리되는 문서가 프로젝트 메모리를 보존하고, 검색 결과는 그 메모리에서 지금 읽어야 할 곳을 가리킨다.
