# AI 에이전트의 메모리는 문서 목차에서 시작된다

AI 에이전트를 위한 좋은 프로젝트 메모리는 문서를 많이 제공하는 것이 아니라, 필요한 문서에 빠르게 도달하고 불필요한 문서는 읽지 않게 하는 **계층적인 목차**를 제공하는 것이다. 디렉터리는 문서의 역할과 상위 목차를 나타내고, 파일명은 개별 목차 항목의 제목이 되며, 각 `README.md`는 다음 하위 목차로 안내한다. 문서가 커지면 파일을 디렉터리와 새로운 README를 가진 하위 목차로 승격해 구조를 확장한다. 이처럼 경로, 파일명, README와 문서 내부 헤딩을 하나의 책처럼 설계하면 AI는 전체 프로젝트를 읽지 않고도 현재 질문에 필요한 스펙, 아키텍처, 테스트, 계획으로 이동할 수 있다.

**Language:** [English edition](ENGLISH.md)

## 문서가 많다고 좋은 메모리는 아니다

문서가 한 디렉터리에 섞여 있거나 `NOTES.md`, `FINAL.md`처럼 역할을 알 수 없는 이름으로 저장되면 에이전트는 파일을 열기 전까지 무엇이 현재 스펙이고, 아키텍처이며, 테스트 방법인지 판단할 수 없다. 반면 같은 주제라도 `docs/spec/CLI_INTERFACE.md`, `docs/arch/CLI_ARCHITECTURE.md`, `docs/test/CLI_INTERFACE.md`처럼 경로가 역할을 드러내면 스펙, 아키텍처, 테스트를 목차만으로 구분할 수 있다.

좋은 프로젝트 메모리는 모든 정보를 항상 제공하지 않는다. 경로와 목차를 통해 현재 작업에 필요한 정보는 빠르게 찾게 하고, 역할이 다른 문서는 읽기 전에 제외하게 한다.

## 프로젝트 문서는 한 권의 책이다

책을 읽을 때 처음부터 끝까지 무작정 읽지 않는다. 먼저 목차를 살펴보고 필요한 부와 장으로 이동한다. 프로젝트 문서도 같은 방식으로 구성할 수 있다.

```text
docs/
├── README.md                         # 책 전체 목차
├── concept/                          # 1부: 핵심 개념
│   ├── README.md                     # 1부 목차
│   └── CONTEXT_CURATION.md           # 장: 컨텍스트 큐레이션
├── spec/                             # 2부: 제품 동작
│   ├── README.md                     # 2부 목차
│   ├── PROJECT_INITIALIZER.md        # 1장: 프로젝트 초기화
│   └── cli/                          # 2장: CLI
│       ├── README.md                 # 2장 목차
│       └── CONFIG_COMMAND.md         # 2장 1절: config 명령
├── arch/                             # 3부: 아키텍처와 제약
│   ├── README.md                     # 3부 목차
│   └── DOCS_STRUCTURE.md             # 장: 문서 구조
└── test/                             # 4부: 테스트
    ├── README.md                     # 4부 목차
    └── CLI_INTERFACE.md              # 장: CLI 회귀 테스트
```

이 구조를 목차의 흐름으로 읽어 보자. `spec/`은 제품 스펙을 모은 최상위 목차이고, 그 아래의 `PROJECT_INITIALIZER.md`는 하나의 목차 항목이다. CLI 문서가 많아지면 `cli/`가 새로운 하위 목차로 승격되고, `cli/README.md`가 그 안의 문서를 안내한다. `CONFIG_COMMAND.md`는 이 하위 목차에 속한 개별 항목이다. 책의 부·장·절로 표현하면 각각 2부, 2부 1장, 2부 2장, 2부 2장 1절에 해당한다.

| 전체 경로 | 목차에서의 역할 | 부·장·절 표기 |
|---|---|---|
| `docs/README.md` | 책 전체를 안내하는 최상위 목차 | 전체 목차 |
| `docs/spec/README.md` | 제품 동작 문서를 모은 영역 목차 | 2부 목차 |
| `docs/spec/PROJECT_INITIALIZER.md` | 프로젝트 초기화 항목 | 2부 1장 |
| `docs/spec/cli/README.md` | CLI 문서를 모은 하위 목차 | 2부 2장 목차 |
| `docs/spec/cli/CONFIG_COMMAND.md` | config 명령 항목 | 2부 2장 1절 |
| `docs/arch/DOCS_STRUCTURE.md` | 문서 구조의 아키텍처 | 3부의 한 장 |
| `docs/test/CLI_INTERFACE.md` | CLI 동작의 테스트 방법 | 4부의 한 장 |

작은 주제는 하나의 파일로 목차에 등록하고, 문서가 많아지면 디렉터리와 `README.md`를 가진 하위 목차로 승격한다. 파일명은 목차 항목의 제목이 되고 전체 경로는 상위 목차부터 그 항목까지 이어지는 주소가 된다.

## 디렉터리 이름은 문서의 역할을 설명한다

각 디렉터리는 문서를 주제별로 분류하는 데 그치지 않는다. 그 안의 정보를 어떻게 해석해야 하는지도 알려준다.

- `concept/`는 문제를 바라보는 관점과 핵심 개념을 설명한다.
- `spec/`는 현재 제품이 지켜야 할 스펙을 정의한다.
- `arch/`는 아키텍처의 이유, 구조, 기술적 제약을 설명한다.
- `test/`는 회귀 테스트와 수동 테스트 방법을 기록한다.
- `report/`는 조사와 측정에서 얻은 근거를 보존한다.
- `plan/`은 현재 진행 중인 작업의 의도를 기록한다.
- `archive/`는 완료된 작업과 역사적 기록을 보존한다.

예를 들어 다음 경로는 그 자체로 하나의 문장이 된다.

```text
docs/spec/cli/CONFIG_COMMAND.md
```

> 이 문서는 현재 제품 스펙 중 CLI의 config 명령을 설명한다.

같은 CLI를 다루더라도 경로에 따라 의미는 달라진다.

```text
docs/arch/CLI_ARCHITECTURE.md
docs/test/CLI_INTERFACE.md
docs/archive/plan/cli-refactor/README.md
```

첫 번째는 아키텍처와 구조, 두 번째는 테스트 방법, 세 번째는 과거 작업의 기록이다. 본문에 비슷한 단어가 등장해도 경로가 정보의 역할과 현재성을 구분한다.

## 파일명은 책의 장 제목이다

다음 파일명은 파일을 구별할 수는 있지만 내용을 설명하지 못한다.

```text
DOCUMENT_1.md
NOTES_NEW.md
FINAL_V2.md
MISC.md
```

반면 다음 이름은 파일을 열기 전부터 범위를 예상하게 한다.

```text
PROJECT_INITIALIZER.md
CLI_INTERFACE.md
LOAD_SNAPSHOT.md
VALIDATION_ARCHITECTURE.md
```

좋은 파일명은 목차만 읽어도 내용을 예상할 수 있는 장 제목과 같다. 그래서 닷닷갓 프로젝트에서는 디렉터리에 `kebab-case`, 지속적으로 관리하는 Markdown 문서에 `UPPER_SNAKE_CASE`를 사용한다. `README.md`는 모든 디렉터리의 예측 가능한 진입점이다.

작성 순서를 나타내는 `API_1.md`보다 행동과 도메인이 드러나는 `CONFIG_COMMAND.md`가 더 좋은 이름이다. 파일명이 안정적이고 구체적이면 사람과 에이전트가 같은 어휘로 문서를 찾고 참조할 수 있다.

## README는 각 책장의 작은 목차다

각 디렉터리의 `README.md`는 단순한 소개문이 아니라 로컬 목차다.

```markdown
# Product specifications

- `CLI_INTERFACE.md` — CLI 전반의 사용자 스펙
- `PROJECT_INITIALIZER.md` — 프로젝트 초기화 동작
- `cli/` — 개별 CLI 명령의 상세 계약
- `plan-mode/` — 계획 모드와 단계 실행 계약
```

에이전트는 이 README를 읽고 디렉터리의 모든 파일을 열지 않은 채 다음에 읽을 문서를 선택할 수 있다. 문서를 추가하거나 옮길 때 가장 가까운 README도 함께 갱신해야 하는 이유다.

## 문서가 커지면 목차의 깊이를 늘린다

처음부터 복잡한 구조를 만들 필요는 없다. 문서가 하나라면 한 파일로 시작한다.

```text
docs/spec/PAYMENT.md
```

해당 도메인이 여러 문서로 성장하면 하위 디렉터리로 승격한다.

```text
docs/spec/payment/
├── README.md
├── LIST_API.md
├── SUMMARY_API.md
└── REFUND_POLICY.md
```

`payment/README.md`는 상위 스펙 목차와 개별 문서 사이를 연결하는 중간 목차가 된다. 에이전트는 다음과 같이 탐색 범위를 좁힌다.

1. `docs/README.md`에서 문서 영역을 선택한다.
2. `docs/spec/README.md`에서 제품 도메인을 선택한다.
3. `docs/spec/payment/README.md`에서 필요한 동작을 찾는다.
4. 관련 문서의 필요한 절만 읽는다.

프로젝트가 커질수록 가능한 컨텍스트는 늘어나지만, 목차가 있으면 현재 작업에 필요한 범위는 계속 작게 유지할 수 있다.

## 좋은 목차는 무엇을 읽지 않을지도 알려준다

CLI 명령의 현재 동작을 수정한다면 먼저 `docs/spec/cli/`를 확인한다. 구현 제약이 필요할 때 `docs/arch/`를 읽고, 회귀 테스트가 필요할 때 `docs/test/`를 확인한다. 과거 결정의 배경이 필요한 경우에만 `docs/archive/`로 이동한다.

문서 구조는 에이전트에게 두 질문의 답을 제공한다.

1. 지금 무엇을 읽어야 하는가?
2. 지금 무엇은 읽지 않아도 되는가?

좋은 프로젝트 메모리는 모든 정보를 매번 프롬프트에 넣는 시스템이 아니다. 필요한 정보로 이동하는 경로와 불필요한 정보를 제외하는 경계를 함께 제공하는 시스템이다.

## 프로젝트 메모리 설계는 주소 체계를 만드는 일이다

AI 에이전트를 위한 메모리를 만든다고 하면 흔히 무엇을 저장할지부터 고민한다. 하지만 그보다 먼저 정보의 주소를 설계해야 한다.

- 경로와 파일명만 보고도 정보의 역할과 내용을 예측할 수 있는가?
- 각 디렉터리에 다음 문서를 안내하는 목차가 있고 현재와 과거가 분리되어 있는가?
- 문서가 늘어나도 목차를 확장해 필요한 항목에 도달할 수 있는가?

디렉터리는 책의 부를 나누고, 파일명은 장의 제목이 되며, README는 다음에 읽을 문서를 안내한다. 문서 내부의 헤딩은 탐색 범위를 절과 항까지 좁힌다.

> AI를 위한 문서 구조를 설계한다는 것은 파일을 보기 좋게 정리하는 일이 아니다. 에이전트가 프로젝트 전체를 읽지 않고도 현재 질문에 필요한 장으로 이동할 수 있도록 책의 목차를 설계하는 일이다.
