# 프로젝트에 사이코메트리 능력을 부여한다면

**Language:** [English edition](ENGLISH.md)

코드를 변경한 뒤에는 무엇을 바꿨는지보다 무엇을 함께 다시 봐야 하는지가 더 어려운 질문이 된다. 수정한 파일과 연결된 스펙, 아키텍처 제약과 테스트를 놓치지 않으려면 프로젝트가 작업의 흔적을 사람이 읽을 수 있는 형태로 기억하고 있어야 한다. 닷닷갓은 이 흔적을 변경 파일에서 역방향으로 읽는 `graph impact`를 프로젝트의 **사이코메트리 능력**처럼 바라본다.

**사람이 관리하는 명시적인 프로젝트 기억은 작업을 시작할 때 목표에서 관련 문서로 향하는 경로와, 작업을 마친 뒤 변경 파일에서 검토 범위로 돌아오는 경로를 함께 만든다.**

## 프로젝트 기억에는 두 탐색 방향이 있다

생명체는 현재 마주한 신호에서 과거 경험과 다음 행동을 떠올린다. 프로젝트도 현재의 목표나 이미 일어난 변경에서 필요한 기억을 찾을 수 있을까?

작업을 시작할 때는 앞으로 만들 결과가 탐색의 출발점이다. 요청과 목표를 이해하고, 관련 규칙과 스펙, 아키텍처와 과거 결정을 찾는다. 반대로 작업을 마친 뒤에는 실제로 변경된 파일이 출발점이 된다. 변경 결과를 보며 함께 검토할 문서와 테스트, 검증 명령을 찾는다.

```text
작업 시작: 목표와 요청 → 필요한 프로젝트 메모리
작업 완료: 변경된 파일 → 함께 검토할 문서·테스트·소스
```

닷닷갓의 `query`는 자연어 질문과 의미가 가까운 문서로 이동하는 첫 번째 경로를 돕는다. `graph impact`는 변경 파일과 관리되는 관계를 사용해 두 번째 경로를 만든다. 둘 다 사람이 관리하는 원문에서 지금 읽어야 할 곳을 좁힌다.

## 사람이 관리하는 흔적이 기억의 원본이다

사이코메트리가 물건에 남은 흔적에서 관련 기억을 읽어내는 가상의 능력이라면, 먼저 읽을 수 있는 흔적이 있어야 한다. 닷닷갓에서는 사람이 읽고 수정할 수 있는 문서를 프로젝트 기억의 원본으로 둔다.

- 스펙은 제품이 현재 보장해야 할 동작을 설명한다.
- 아키텍처 문서는 설계 이유와 제약을 남긴다.
- 테스트 문서는 무엇을 어떻게 검증하는지 설명한다.
- README 목차와 Markdown 링크는 다음 문서로 향하는 경로를 만든다.
- 트레이서빌리티는 스펙과 구현, 테스트와 검증 명령을 명시적으로 연결한다.

그래프 인덱스와 벡터 캐시는 이 원본을 탐색하기 위한 파생 데이터다. 캐시를 삭제해도 관리되는 프로젝트 기억은 문서에 남으며, 그래프와 벡터 데이터는 문서와 저장소 구조에서 다시 계산할 수 있다. 검색 결과는 읽을 원문의 주소를 제공하고, 그래프 점수는 검토 우선순위를 나타낸다. 실제 동작은 관련 원문, 코드와 테스트를 함께 확인해 판단한다.

## graph impact는 흔적을 역방향으로 읽는다

문서에서 구현과 테스트를 가리키는 관계가 남아 있다면 변경 파일에서도 그 관계를 거슬러 올라갈 수 있다.

```bash
dotdotgod graph impact . \
  --changed packages/cli/src/commands/query.mjs \
  --yml
```

여러 파일이 하나의 변경을 구성한다면 `--changed`를 반복한다. 각 변경 파일은 그래프 탐색의 시작점이 되고, 공통으로 연결된 스펙이나 테스트는 전체 검토 순위에서 하나로 합쳐진다.

인덱스 그래프는 설정된 트레이서빌리티, Markdown 링크, README 경로, 제목, 패키지 메타데이터, 스크립트와 리소스, 의존성, 메모리 영역처럼 사람이 관리하거나 저장소에서 결정론적으로 추출할 수 있는 관계를 사용한다. Impact 순위는 변경 파일을 시작점으로 하는 weighted Personalized PageRank에 최대 `80`점, 메모리 정책에 최대 `20`점을 배정하며 직접·검증·semantic·노드 타입 증거에는 별도 점수나 정렬 보너스를 주지 않는다. 로컬 query 캐시를 사용할 수 있으면 변경 파일 벡터를 저장하거나 인덱스 그래프를 변경하지 않고 bounded request-local 다국어 `vector_similarity` overlay를 후보 탐색과 PPR에 추가한다. 벡터 준비가 실패하면 구조 관계만으로 결과를 반환한다.

다음은 출력의 핵심 형태를 줄여 표현한 예시다. 실제 경로, 점수와 이유는 저장소 상태와 설정에 따라 달라진다.

```yaml
impact:
  changed_files:
    - packages/cli/src/commands/query.mjs
  groups:
    docs:
      items:
        - path: docs/spec/cli/QUERY.md
          score: 65.4
          reasons: [implemented_by, routes_to]
    tests:
      items:
        - path: packages/cli/test/e2e.test.mjs
          score: 58.1
          reasons: [verified_by]
  recommended_actions:
    - review_related_docs
    - run_related_tests
    - run_dotdotgod_validate
```

`score`는 각 후보를 먼저 검토할 가치를 나타낸다. `reasons`는 구조화된 추적 관계나 직접 연결처럼 각 후보가 목록에 포함된 근거를 보여준다. 결과를 문서, 테스트, 소스와 명령으로 나누면 에이전트도 다음 행동을 제한된 범위에서 선택할 수 있다.

## 사이코메트리 비유의 한계

`graph impact`는 제한된 상위 검토 후보를 제공한다. 결과 밖에도 관련 항목이 남을 수 있으며, 높은 점수를 받은 파일의 수정 여부는 연결된 원문과 테스트를 확인해 판단한다.

결과의 품질은 프로젝트가 남긴 흔적의 품질에 의존한다. 오래된 README, 빠진 구현 관계와 여러 동작을 동시에 담당하는 큰 파일은 검토 범위를 넓고 덜 구체적으로 만든다. 분명한 문서 역할과 현재 상태를 설명하는 트레이서빌리티와 테스트 관계는 변경 파일에서 더 유용한 검토 후보를 찾게 한다.

따라서 `graph impact`의 결과는 다음 검토 목록으로 사용한다. 최종 판단은 연결된 원문과 테스트를 확인한 뒤 내린다.

```text
파일 변경
  → graph impact
  → 관련 원문과 테스트 검토
  → 필요한 코드와 문서 갱신
  → 테스트와 dotdotgod validate 실행
```

## 사람이 프로젝트 기억을 관리한다

사람이 이해하기 좋은 이름, 경로, 문서 역할과 관계는 AI에게도 프로젝트를 읽는 인지 단서가 된다. 작업을 시작할 때는 목표에서 필요한 원문으로 향하고, 작업을 마칠 때는 변경된 파일에서 함께 검토할 원문으로 돌아온다.

이 두 방향의 품질은 같은 관리 원본에서 시작된다. 사람이 문서와 트레이서빌리티를 현재 상태에 맞게 고치면 에이전트의 검색 경로와 변경 검토 경로도 함께 달라진다.

> 프로젝트의 사이코메트리는 사람이 관리해 온 기억에서 놓치기 쉬운 다음 검토 경로를 읽는 능력이다.
