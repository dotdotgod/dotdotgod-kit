# 닷닷갓 query는 자연어 질문에서 관련 문서를 어떻게 찾는가

문서 목차는 역할과 경로를 알고 있을 때 가장 빠른 탐색 방법이다. 하지만 사용자의 질문과 문서의 파일명은 같은 표현을 사용하지 않을 수 있고, 한국어 질문과 영어 문서처럼 언어가 다를 수도 있다. **`dotdotgod query`는 자연어 질문과 의미가 가까운 문서 구간을 로컬에서 찾아, 에이전트가 읽어야 할 관리 원문으로 이동하는 경로를 제공한다.**

**Language:** [English edition](ENGLISH.md)

**Published:** [Velog](https://velog.io/@vgb3766/%EB%8B%B7%EB%8B%B7%EA%B0%93-query%EB%8A%94-%EC%9E%90%EC%97%B0%EC%96%B4-%EC%A7%88%EB%AC%B8%EC%97%90%EC%84%9C-%EA%B4%80%EB%A0%A8-%EB%AC%B8%EC%84%9C%EB%A5%BC-%EC%96%B4%EB%96%BB%EA%B2%8C-%EC%B0%BE%EB%8A%94%EA%B0%80)

문서는 프로젝트 메모리의 원본으로 남는다. 임베딩과 검색 결과는 질문에서 그 원본까지 이어지는 파생 탐색 데이터다.

## 경로를 모를 때 의미가 탐색의 출발점이 된다

다음 질문을 생각해 보자.

> Load가 오래된 계획을 기본 컨텍스트에서 제외하는 이유는 무엇인가?

관련 내용은 `LOAD_PROJECT.md`, `MEMORY_AREA_CONFIG.md` 또는 컨텍스트 큐레이션 문서에 있을 수 있다. 파일명만 검색하면 질문에 등장한 “오래된 계획”과 문서에서 사용하는 `archive`, `local memory`, `stale` 같은 표현을 연결하기 어렵다.

`query`는 자유 형식 질문을 받아 의미가 가까운 Markdown 문단을 찾는다.

```bash
dotdotgod query . \
  "Load가 오래된 계획을 기본 컨텍스트에서 제외하는 이유" \
  --limit 5
```

`<root>` 뒤의 여러 인자는 하나의 검색어로 합쳐진다. `--limit`은 1부터 100까지 지정할 수 있고 기본값은 30이다. 이 수는 문단 수가 아니라 서로 다른 Markdown 파일 수를 제한한다.

## 검색 대상도 Docs-first 경계를 따른다

query는 `docs/` 아래의 Markdown 문서를 검색 대상으로 삼고 `load.documentationSummary.exclude` 정책으로 범위를 정한다.

기본적으로 다음 본문은 제외된다.

```text
docs/plan/
docs/archive/
```

활성 계획과 과거 기록은 필요할 때 README 목차와 명시적인 경로로 읽는다. 숨김 경로, 비밀 정보로 보이는 경로, 건너뛰도록 설정된 디렉터리도 임베딩 대상이 아니다.

이 범위 정책은 현재 공유 문서와 로컬 작업 기록의 역할을 검색 단계에서도 유지한다.

## Markdown을 제목 계층에 따라 나눈다

검색 단위에는 한 절의 의미와 이를 해석할 문맥이 함께 들어가야 한다. 닷닷갓은 Markdown의 제목 계층을 따라 문서를 나누고, 본문 조각을 최대 1,600자로 제한한 뒤 경로와 제목 정보를 함께 추가한다.

```text
docs/spec/LOAD_PROJECT.md
└── Focused Query
    └── query searches shared documentation ...
```

각 문서 구간에는 저장소 기준 경로, 상위부터 현재까지의 제목 계층, 제한된 본문 조각이 들어간다. 경로와 제목은 검색 결과를 해석할 주소를 제공하고, 본문은 질문과 비교할 의미를 제공한다.

## 다국어 E5 모델을 로컬에서 실행한다

현재 query가 지원하는 모델은 `Xenova/multilingual-e5-small` 하나다. `@huggingface/transformers`를 통해 로컬에서 실행하며 문서 본문을 원격 임베딩 API로 보내지 않는다.

E5 모델의 사용 방식에 따라 입력에는 서로 다른 prefix를 붙인다.

```text
query: Load가 오래된 계획을 기본 컨텍스트에서 제외하는 이유
passage: path: docs/spec/LOAD_PROJECT.md ...
```

검색어에는 `query: `를, 문서 구간에는 `passage: `를 사용한다. 모델은 각각을 정규화된 384차원 float32 벡터로 변환한다.

모델 파일이 사용자 환경에 없으면 첫 실행에서 런타임의 사용자 단위 캐시에 내려받을 수 있다. 현재는 원격 제공자 선택이나 다른 임베딩 모델 프로필을 지원하지 않는다.

## 모든 문서 구간과 의미 유사도를 직접 비교한다

query는 질문과 모든 문서 구간의 의미가 얼마나 가까운지 정확하게 비교한다(cosine similarity). 정규화된 벡터가 비슷한 방향을 가리킬수록 높은 점수를 받는다. 현재의 작은 로컬 문서 모음에서는 일부 가까운 후보만 빠르게 추리는 검색 방식(approximate nearest neighbor)을 위한 별도 인덱스가 필요하지 않다.

```text
질문을 의미 좌표로 변환
  → 모든 문서 구간과 의미 유사도 비교
  → 제목 계층과 경로에 같은 표현이 있으면 가산점
  → 점수와 경로 순으로 안정 정렬
  → Markdown 경로별 최고 결과 하나 선택
```

질문의 단어가 결과 경로나 제목 계층에 직접 등장하면 작은 가산점을 더한다(lexical boost). 의미가 가까운 문서를 중심에 두면서 명시적인 경로와 제목 일치도 함께 반영한다.

정렬 후에는 Markdown 경로로 중복을 제거한다. 한 문서에서 여러 문단이 높은 점수를 받아도 가장 높은 문단 하나만 그 파일을 대표한다. 따라서 결과가 한두 개의 긴 문서로 채워지는 것을 줄이고, 에이전트가 검토할 문서의 폭을 확보한다.

## 변경되지 않은 문단은 다시 임베딩하지 않는다

파생 벡터 데이터는 Git에서 제외된 저장소별 캐시에 저장된다.

```text
.dotdotgod/vectors/
├── manifest.json
├── chunks.jsonl
└── embeddings.f32
```

`manifest.json`은 스키마, 모델, 차원, 제외 정책과 갱신 정보를 기록한다. 문서 구간과 경로 정보는 `chunks.jsonl`에, float32 벡터는 `embeddings.f32`에 저장된다.

각 문단의 fingerprint가 같으면 기존 벡터를 재사용한다. 변경되거나 새로 생긴 문단만 임베딩하고, 삭제된 문단은 캐시를 다시 쓸 때 제거한다.

캐시가 손상되었거나 일부 파일이 없거나, 스키마·모델·차원이 현재 설정과 맞지 않으면 전체를 다시 만든다. 각 산출물은 임시 파일에 쓴 뒤 atomic rename으로 교체해 불완전한 쓰기의 위험을 줄인다.

이 캐시는 관리 문서에서 언제든 다시 만들 수 있는 파생 데이터다.

## 결과는 원문을 읽기 위한 제한된 후보 목록이다

사람이 읽는 기본 출력은 간결하게 유지된다. `--json`을 사용하면 검색어, 모델, 차원, 인덱스 정보와 각 결과의 구조화된 데이터를 확인할 수 있다.

각 결과는 chunk ID와 저장소 기준 Markdown 경로, 제목 계층, 제한된 본문 excerpt를 제공한다. 최종 점수에는 같은 표현에 주는 가산점이 반영되며, 원래 의미 유사도 점수도 함께 확인할 수 있다.

높은 점수는 질문과 의미가 가까운 원문 후보를 가리킨다. 기본 검색 범위에 포함되는 `docs/spec/`의 제품 계약과 `docs/concept/`의 설명 문서는 같은 단어를 사용해도 역할이 다르다. 에이전트는 결과의 경로와 제목으로 역할을 확인한 뒤 관리되는 원문을 읽는다.

## query와 graph impact는 다른 질문에 답한다

두 기능 모두 관련 문서를 찾지만 출발점과 신호가 다르다.

| 기능 | 출발점 | 주요 신호 | 목적 |
|---|---|---|---|
| `query` | 자연어 질문 | 다국어 의미 검색과 같은 표현에 주는 작은 가산점 | 의미가 가까운 문서 찾기 |
| `graph impact` | 변경 파일 | 추적 관계, 링크, PPR과 프로젝트 정책 | 함께 검토할 항목 찾기 |

query는 별도의 로컬 벡터 캐시를 사용한다. graph impact의 기본 랭킹은 결정론적인 관계와 단어 일치 기반 경로 탐색(lexical routing)을 사용하며, 임베딩 유사도는 기본 경로에 포함하지 않는다.

Load는 자연어 초점이 있을 때 query 결과를 문서 지도와 함께 사용한다. 반면 코드나 문서를 변경한 뒤에는 graph impact가 다음 검토 경로를 찾는다.

## 의미 검색과 문서 목차가 하나의 읽기 경로를 만든다

의미 검색은 경로를 모르는 질문에서 후보를 찾고, 경로와 README는 각 후보 문서의 역할을 설명한다.

```text
질문
  → query로 후보 경로 찾기
  → README와 메모리 영역으로 역할 확인
  → 관리되는 원문의 필요한 절 읽기
```

> 벡터 검색은 질문의 표현과 문서의 표현이 달라도 에이전트가 읽어야 할 원문 주소를 찾아준다.
