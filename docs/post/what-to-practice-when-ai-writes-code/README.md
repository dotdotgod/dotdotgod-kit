# AI가 코드를 쓰는 시대에는 무엇을 훈련해야 하는가

**Language:** [English edition](ENGLISH.md)

AI가 코드를 생성하면서 개발자가 익혀야 할 능력의 무게가 달라지고 있다. 키보드로 코드를 빠르게 입력하는 능력의 중요도는 낮아지는 반면, 어떤 작업이 필요한지 파악하고 생성된 코드를 평가하며 설계와 복잡도를 관리하는 능력은 더 중요해진다. **AI를 잘 사용하려면 줄어드는 훈련과 더 깊어져야 하는 훈련을 구분해야 한다.**

AI는 전문가가 되기 위해 넘어야 했던 몇 가지 초기 장벽을 크게 낮춘다. 그 결과 한 사람이 만들 수 있는 것과 시도할 수 있는 가능성은 빠르게 커진다. 이 변화가 실제 역량으로 이어지려면 생성 속도만큼 사고와 판단도 함께 훈련해야 한다.

## 타이핑 속도의 중요도는 낮아진다

코드를 직접 입력하던 때에는 생각한 내용을 정확한 문법으로 빠르게 옮기는 능력이 생산성에 큰 영향을 주었다. 자주 쓰는 문법과 API를 기억하고, 에디터와 단축키에 익숙해지고, 타이핑 속도를 높이는 훈련이 실제 작업 시간을 줄였다.

AI가 코드의 초안을 작성하면 손으로 입력하는 시간이 크게 줄어든다. 자연어로 요구사항을 설명하거나 기존 코드를 기준으로 변경을 요청하면 여러 파일에 걸친 구현도 짧은 시간 안에 만들어진다. 타이핑은 계속 필요하지만 생산성을 결정하는 중심 능력에서 점차 멀어진다.

```text
이전: 생각 → 문법과 API를 기억 → 직접 입력 → 실행
현재: 생각 → 작업을 설명 → AI가 생성 → 검토와 수정 → 실행
```

줄어든 것은 코드를 표현하는 데 필요한 기계적인 시간이다. 무엇을 만들어야 하는지 이해하고 결과가 적절한지 판단하는 시간은 여전히 남는다.

## 코드를 작성하기 전의 파악은 더 쉬워진다

개발자는 구현을 시작하기 전에 낯선 코드와 요구사항을 이해해야 한다. 관련 파일을 찾고, 호출 관계를 따라가고, 기존 설계의 의도와 제약을 파악하며, 변경이 미칠 범위를 예상한다. 이 과정에서 필요한 정보를 찾는 속도가 느리면 실제 구현에 도달하기까지 많은 시간이 든다.

AI는 이 탐색을 압축한다. 코드베이스에서 관련 부분을 찾고, 여러 파일의 역할을 요약하고, 익숙하지 않은 라이브러리와 개념을 설명하며, 가능한 변경 지점을 제안한다. 개발자는 더 짧은 시간에 문제의 전체 형태를 볼 수 있다.

이것은 인지능력의 확장에 가깝다. AI가 더 넓은 범위에서 신호를 찾고 관계를 후보로 제시하면, 사람은 그 결과를 바탕으로 중요한 차이를 구분하고 현재 작업에 필요한 맥락을 선택할 수 있다. 이전에는 탐색 비용 때문에 접근하기 어려웠던 영역도 검토 가능한 범위 안으로 들어온다.

## 생성 능력보다 평가 능력을 더 훈련해야 한다

코드가 빠르게 생성될수록 생성된 결과를 평가하는 능력이 생산성과 품질을 결정한다. 코드를 읽고 동작을 설명할 수 있어야 하며, 요구사항을 만족하는지, 기존 계약을 깨뜨리지 않는지, 오류와 보안 위험이 없는지 판단해야 한다.

평가 능력은 문법 오류를 찾는 수준을 넘어선다. 코드가 해결해야 할 문제를 정확히 이해했는지, 책임이 적절한 위치에 놓였는지, 테스트가 중요한 경계를 검증하는지, 변경 이후에도 유지보수할 수 있는지를 함께 본다.

AI가 만든 코드가 자연스럽고 완성도 높아 보일수록 이 훈련은 중요해진다. 읽기 좋은 표현과 올바른 설계는 같은 의미가 아니며, 실행되는 코드와 운영할 수 있는 코드도 같지 않다. 표면적인 완성도에 설득되지 않고 근거를 확인하는 안목이 필요하다.

## 설계와 복잡도 관리의 가치는 더 커진다

AI는 코드를 빠르게 추가할 수 있다. 방향과 경계가 불분명한 상태에서도 그럴듯한 구현을 계속 생성할 수 있기 때문에 복잡도 역시 빠르게 증가할 수 있다. 생성 비용이 낮아질수록 무엇을 만들지 선택하고 어디에서 멈출지 결정하는 능력이 중요해진다.

좋은 설계는 요구사항을 좁고 명확한 책임으로 나누고, 변경이 퍼지는 범위를 제한하며, 각 부분의 관계를 설명할 수 있게 한다. 복잡도 관리는 지금 필요한 기능과 나중에 필요할 가능성을 구분하고, 중복과 예외가 쌓이는 지점을 발견하며, 삭제하거나 단순화할 대상을 선택하는 일이다.

이 능력은 AI가 생겼다고 약해지지 않는다. 생성 속도가 빨라지면서 설계 판단의 결과가 더 짧은 시간 안에 더 큰 규모로 나타난다. 좋은 설계는 AI의 생산성을 증폭하고, 나쁜 설계는 AI가 만드는 복잡도를 증폭한다.

## 낮아지는 훈련과 깊어지는 훈련을 구분한다

| 중요도가 낮아지는 훈련 | 더 깊어져야 하는 훈련 |
|---|---|
| 코드와 보일러플레이트를 빠르게 입력하기 | 작업의 목적과 성공 조건 정의하기 |
| 모든 문법과 API를 기억하기 | 필요한 정보를 찾고 맥락을 선택하기 |
| 익숙하지 않은 코드를 처음부터 해독하기 | AI가 제시한 설명과 관계를 검증하기 |
| 구현 초안을 손으로 완성하기 | 생성된 코드의 동작과 품질 평가하기 |
| 반복적인 변환을 직접 수행하기 | 설계 경계와 복잡도 관리하기 |

왼쪽의 능력이 완전히 사라지는 것은 아니다. 직접 작성하고 디버깅한 경험은 오른쪽의 판단을 만드는 기반이 된다. 변화의 핵심은 숙련의 목적과 투자할 시간의 비율이 달라진다는 데 있다.

## 몇 개의 장벽이 낮아지면 가능성은 크게 넓어진다

전문가가 되기까지의 과정에는 지식의 깊이와 별개로 많은 진입 비용이 있었다. 문법을 익히고, 개발 환경을 구성하고, 낯선 오류 메시지를 해석하고, 반복되는 코드를 작성하는 초기 장벽이 시도를 느리게 만들었다.

AI는 이 중 여러 장벽을 낮춘다. 아이디어를 실행 가능한 초안으로 옮기는 시간이 줄고, 익숙하지 않은 분야에서도 첫 번째 결과를 만들 수 있다. 개발자는 더 많은 실험을 수행하고, 작은 팀은 더 넓은 제품 범위를 다루며, 개인도 이전보다 큰 문제에 접근할 수 있다.

이 장벽이 낮아졌다고 전문성이 사라지는 것은 아니다. 더 많은 사람이 출발선에 설 수 있고, 전문가는 이미 가진 지식과 판단을 훨씬 넓은 범위에 적용할 수 있다. 생산성과 가능성이 함께 커지는 이유다.

## 사고와 판단의 게으름을 경계한다

AI가 즉시 답과 코드를 제시하면 이해하기 전에 결과를 받아들이기 쉽다. 요구사항을 구체화하지 않은 채 구현을 요청하고, 생성된 코드를 충분히 읽지 않고, 테스트가 통과했다는 사실만으로 판단을 끝낼 수 있다.

이 습관이 반복되면 결과를 만드는 속도는 빨라져도 스스로 문제를 구조화하고 오류를 발견하는 능력은 약해진다. AI를 통해 절약한 시간을 더 나은 질문, 설계 검토, 코드 읽기와 결과 검증에 다시 투자해야 한다.

AI의 한계를 안다는 것은 모든 결과를 의심한다는 뜻이 아니다. 어떤 종류의 오류가 가능한지 알고, 중요한 판단에 필요한 근거를 확인하며, 결과에 대한 책임을 사람이 가진다는 뜻이다. 도구가 유능해질수록 판단을 생략할 유혹도 커지므로 의식적인 검토 습관이 필요하다.

## 더 적게 입력하고 더 깊게 판단한다

AI 시대의 개발자는 코드를 입력하는 데 쓰던 시간을 문제를 이해하고, 설계를 선택하고, 결과를 검토하는 데 사용할 수 있다. 초기 장벽이 낮아지면서 더 많은 사람이 더 큰 가능성을 탐색할 수 있고, 전문가는 자신의 안목을 더 넓은 범위에 적용할 수 있다.

훈련의 중심도 함께 이동한다. 타이핑과 암기의 비중은 줄어들고, 문제 정의, 맥락 선택, 코드 평가, 설계와 복잡도 관리의 비중은 커진다. 이 변화를 이해하면 AI의 생산성을 활용하면서도 사고와 판단의 주도권을 유지할 수 있다.

> AI가 코드를 더 많이 쓰게 될수록 우리는 무엇을 만들지, 무엇이 좋은 코드인지, 어디까지 믿을지를 더 깊게 훈련해야 한다.
