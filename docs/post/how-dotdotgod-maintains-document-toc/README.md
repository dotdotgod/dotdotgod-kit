# 닷닷갓 킷은 문서 목차를 어떻게 유지하는가

앞선 글에서는 프로젝트의 하위 디렉터리와 파일명이 AI 에이전트를 위한 책의 목차라고 설명했다. 그러나 목차를 처음 한 번 잘 만드는 것만으로는 충분하지 않다.

프로젝트가 성장하면 문서는 추가되고, 이름이 바뀌고, 여러 파일로 분리된다. 작업이 끝난 계획은 과거 기록이 되고, 새로운 기능은 스펙과 테스트를 요구한다. 관리 장치가 없다면 처음에는 깔끔했던 목차도 빠르게 무너진다.

- 파일이 추가됐지만 README 목차에는 등록되지 않는다.
- 문서를 옮겼지만 기존 링크는 이전 경로를 가리킨다.
- 완료된 계획이 계속 활성 작업처럼 남아 있다.
- 하나의 문서가 너무 커져 여러 책임을 동시에 다룬다.
- 스펙이 바뀌었지만 관련 테스트나 구현 링크는 갱신되지 않는다.

닷닷갓 킷은 문서 구조를 권장사항으로만 두지 않는다. 초기화, 공통 규칙, 로컬 목차, 자동 검증, 추적 관계, 영향 분석과 아카이브 흐름을 함께 사용해 문서 체계를 유지한다.

## 1. 프로젝트를 시작할 때 기본 목차를 만든다

닷닷갓 킷은 프로젝트 초기화 단계에서 기본 문서 구조를 만든다.

```text
AGENTS.md
CLAUDE.md
CODEX.md
docs/
├── README.md
├── spec/
│   └── README.md
├── arch/
│   └── README.md
├── test/
│   └── README.md
├── plan/
│   └── README.md
└── archive/
    └── README.md
```

빈 디렉터리만 만드는 것이 아니다. 각 README는 영역의 역할과 문서를 배치하는 기준을 설명한다. 문서를 쓰기 전에 책의 부와 기본 목차부터 만드는 셈이다.

에이전트가 달라져도 같은 구조를 사용한다.

- `AGENTS.md`는 모든 에이전트가 공유하는 작업 규칙이다.
- `CLAUDE.md`와 `CODEX.md`는 공통 규칙으로 연결되는 얇은 진입점이다.
- `docs/README.md`는 프로젝트 문서 전체를 탐색하는 시작점이다.

따라서 Pi, Claude Code, Codex가 서로 다른 문서 체계를 만들지 않고 같은 경로와 용어를 공유할 수 있다.

## 2. 각 README를 로컬 목차로 관리한다

닷닷갓 킷은 모든 문서를 하나의 거대한 목차에 나열하지 않는다. 각 디렉터리의 `README.md`가 자기 영역의 로컬 목차를 담당한다.

```text
docs/README.md
    ↓
docs/spec/README.md
    ↓
docs/spec/cli/README.md
    ↓
docs/spec/cli/LOAD_SNAPSHOT.md
```

각 README에는 중요한 문서와 하위 디렉터리, 상태, 한 줄 설명을 기록한다. 문서를 추가하거나 이름을 바꾸거나 분리하거나 아카이브할 때는 가장 가까운 README를 같은 변경에서 갱신한다.

이 규칙 덕분에 README는 소개문이 아니라 실제 문서 탐색을 위한 라우팅 테이블이 된다.

## 3. 문서가 성장하면 새로운 목차 단계로 승격한다

작은 주제는 하나의 집중된 문서로 시작한다.

```text
docs/spec/PAYMENT.md
```

한 도메인이 여러 문서로 성장하면 별도의 디렉터리와 README를 갖는 구조로 승격한다.

```text
docs/spec/payment/
├── README.md
├── LIST_API.md
├── SUMMARY_API.md
└── REFUND_POLICY.md
```

이 방식은 하나의 목차가 지나치게 길어지는 것을 막고, 거대한 문서가 여러 책임을 동시에 설명하는 것도 방지한다. 문서가 늘어날 때 파일만 추가하는 것이 아니라 탐색 계층도 함께 조정하는 것이다.

## 4. 이름과 구조를 자동으로 검증한다

문서 규칙은 작성자의 기억에만 의존해서는 오래 유지되지 않는다. 닷닷갓 CLI는 프로젝트 문서가 정해진 구조를 따르는지 검사한다.

```bash
node packages/cli/bin/dotdotgod.mjs validate . \
  --include-local-memory \
  --check-index
```

검증은 다음과 같은 문제를 찾는다.

- 필요한 기본 문서가 존재하는가
- Markdown 링크가 유효한가
- 문서 이름과 경로가 규칙에 맞는가
- README 인덱스가 필요한 위치에 있는가
- 문서 크기가 관리 가능한 범위에 있는가
- 설정과 추적 정보가 유효한가
- 문서 인덱스가 현재 파일 상태와 일치하는가

책을 출간하기 전에 목차, 상호 참조와 누락된 페이지를 확인하는 교정 과정과 비슷하다. 문서 구조를 사람의 주의력에만 맡기지 않고 코드처럼 검사한다.

## 5. 스펙과 구현, 테스트를 연결한다

목차가 잘 구성되어 있어도 문서가 실제 코드와 분리되어 있다면 프로젝트 메모리의 신뢰도는 낮아진다.

닷닷갓 킷은 중요한 동작 스펙에 구조화된 추적 정보를 기록할 수 있다. 이 정보는 스펙을 다음 항목과 연결한다.

- 구현 파일
- 테스트 파일
- 관련 문서
- 검증 명령어
- 의존하는 계약

CLI 동작이 변경되면 에이전트는 스펙만 읽고 끝내지 않는다. 관련 구현과 회귀 테스트, 검증 명령까지 함께 확인할 수 있다. 책의 목차가 장의 위치뿐 아니라 관련 장과 참고 문헌까지 안내하는 셈이다.

이 연결은 스펙과 구현, 테스트가 서로 다른 방향으로 변하는 문제를 발견하기 쉽게 만든다.

## 6. 변경 파일에서 관련 목차를 역으로 찾는다

실제 개발에서는 문서에서 코드로만 이동하지 않는다. 코드를 먼저 수정한 뒤 어떤 스펙과 테스트가 영향을 받는지 확인해야 할 때도 많다.

닷닷갓 킷은 문서 링크, README 경로, 추적 정보와 프로젝트 그래프를 사용해 변경 파일 주변의 영향을 탐색한다.

```bash
dotdotgod graph impact --changed <path>
```

설정 코드를 변경했다면 관련된 동작 스펙, 아키텍처 문서, 테스트, 검증 명령과 소스 파일을 함께 찾을 수 있다. 문서 체계가 수동적인 보관소가 아니라 변경 검토에 사용되는 인터페이스가 되는 것이다.

그래프와 인덱스가 원본 문서를 대신하지는 않는다. 원본 문서가 프로젝트의 진실이고, 그래프는 필요한 문서로 빠르게 이동하게 하는 색인이다.

## 7. 현재 계획과 과거 기록을 분리한다

문서 체계가 오래될수록 현재 정보와 역사적 정보의 구분이 중요해진다.

진행 중인 작업은 다음 경로에 기록한다.

```text
docs/plan/<task-slug>/README.md
```

계획에는 목표, 범위, 대상 파일, 위험, 구현 순서, 검증 방법과 진행 상태가 들어간다. 작업이 끝나면 계획을 아카이브로 이동한다.

```text
docs/archive/plan/<task-slug>/
```

`docs/archive/README.md`는 완료된 작업을 찾는 역사 목차로 남는다. 과거를 삭제하지 않으면서도 현재 작업과 섞이지 않게 하는 방식이다.

에이전트는 모든 아카이브 본문을 항상 읽지 않는다. 먼저 역사 목차를 확인하고, 특정한 과거 결정이 필요할 때만 관련 기록을 연다.

## 8. 전체 책이 아니라 필요한 목차부터 불러온다

닷닷갓 킷은 저장소 전체를 프롬프트에 넣는 대신 제한된 프로젝트 메모리 지도를 먼저 만든다.

지도에는 다음과 같은 정보가 포함된다.

- 캐시와 인덱스가 최신인지
- 어떤 메모리 영역이 있는지
- 현재 계획이 어디에 있는지
- 문서가 어떤 커뮤니티를 이루는지
- 아카이브를 어느 범위까지 포함할지
- 다음에 어떤 README를 읽어야 하는지

에이전트는 이 지도를 받은 뒤 현재 요청에 필요한 문서만 선택한다.

```text
AGENTS.md
  → docs/README.md
  → docs/spec/README.md
  → docs/spec/cli/README.md
  → 관련 스펙
  → 관련 아키텍처와 테스트
```

과거 기록이 필요하지 않다면 아카이브 본문은 읽지 않는다. 목차 중심의 문서 구조가 실제 컨텍스트 절약 방식으로 이어지는 지점이다.

## 문서 체계는 작업 흐름으로 유지된다

닷닷갓 킷은 초기화와 공통 에이전트 규칙으로 기본 목차를 만들고, 각 README를 로컬 목차로 사용한다. 문서가 성장하면 도메인 디렉터리로 승격하고, 자동 검증과 영향 분석으로 링크와 추적 관계를 점검한다. 계획과 아카이브의 수명주기는 현재와 과거를 분리하며, 제한된 메모리 로딩은 필요한 목차만 선택한다.

문서 체계는 잘 정리된 초기 상태만으로 유지되지 않는다. 문서가 추가되고, 변경되고, 분리되고, 완료되는 모든 과정에 목차를 갱신하는 규칙이 포함되어야 한다.

닷닷갓 킷이 관리하려는 것은 Markdown 파일의 집합이 아니다. 사람과 여러 AI 에이전트가 같은 방식으로 읽고, 변경하고, 검증할 수 있는 **살아 있는 프로젝트 메모리 체계**다.
