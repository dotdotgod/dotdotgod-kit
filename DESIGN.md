# Design

## Visual Character

Dotdotgod operational tools use a restrained technical plotting-desk language: pale neutral work surfaces, graphite text, precise rules, and saturated colors only when they encode state or evidence.

## Color Roles

- Graphite: primary text, strong boundaries, and inactive controls.
- Cobalt: current selection, changed roots, focus, and primary action.
- Green: verification and test evidence.
- Amber: inferred semantic evidence and contracts requiring interpretation.
- Violet: maintained documentation nodes.
- Pale neutral fields: graph plotting and reading surfaces.

Color must not carry meaning alone; labels, relation names, direction, and list text remain present.

## Typography

Use the platform sans stack for interface prose and controls. Use the platform monospace stack only for repository paths, commands, identifiers, scores, and other measurements. Maintain obvious size and weight steps while keeping dense operational views compact.

## Layout and Components

Operational graph surfaces use fixed information rails around one dominant plotting field. Prefer square or lightly rectangular controls, one-pixel rules, compact tabular figures, and synchronized graph/list inspection over card grids.

Changed files are explicit roots, not ranked results. Impact score controls node size; graph distance is never presented as ranking strength.

## Interaction and Motion

Graph selection and accessible list selection must remain synchronized. Hover or focus should emphasize immediate neighbors without removing the ranked evidence path. Motion is brief and functional; reduced-motion preferences remove camera animation.

## Accessibility

Every canvas or WebGL view requires semantic list parity for its actionable content. Use native controls, visible focus rings, live status for recalculation, high-contrast text, and a usable fallback when accelerated rendering is unavailable.
